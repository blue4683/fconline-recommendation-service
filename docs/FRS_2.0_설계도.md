## 1. 목표

**한 줄 목표**: 자연어로 "예산·급여·팀컬러·포메이션" 조건을 말하면, 그 조건을 모두 지키는 11인 스쿼드를 근거와 함께 추천한다.

**2024년에 발견한 미해결 문제와 이번 범위** (✅ velog `[FRS] 스쿼드 추천 개발 관련 계획`, 2024-09-11)

| # | 기존 문제 | v3에서 하는 것 | v3에서 하지 않는 것 |
|---|---|---|---|
| 1 | 기재된 포지션에만 추천됨 | [실] 평가 오류를 정정하고 원인 후보를 측정한다 (Stage 2). 모델 확률을 "확장 배치" 후보 신호로만 쓴다 (Stage 3-A) | 실제 활용 적합성을 해결했다고 주장하지 않는다. 등록 포지션을 정답으로 학습하는 구조의 한계이며 정답 데이터가 없다 |
| 2 | `used` 단일 지표의 한계 | 성능 점수를 별도로 정의하고 가격·급여는 제약으로 다뤄 "싸고 좋은" 조합을 탐색한다 (Stage 3) | 시세를 실제 구매 가능 가격으로 보장하지 않는다. 사용한 가격의 관측 시각과 기준을 표시한다 |
| 3 | 급여 제한 미반영 | 급여를 제약으로 처리하는 탐색기·검증기 (Stage 3) | 허용된 데이터 경로가 없으면 실데이터를 수집하지 않는다 |

**설계 원칙** 🔶
1. **계산은 코드가 한다.** 합계, 단위 변환, 제약 판정은 LLM이 하지 않는다.
2. **조합은 탐색기가 한다.** LangGraph는 과정을 연결할 뿐이다.
3. **최종 스쿼드는 코드가 확정하고 코드가 렌더링한다.** 선수·강화 단계·금액·합계는 코드가 표로 출력한다. LLM은 허용된 근거 필드만으로 서술한다.
4. **모르는 값은 0이 아니다.** 상태가 `ok`가 아니거나 유효시각이 지난 가격·급여는 계산에 쓰지 않는다.
5. **한 요청은 한 스냅샷으로 계산한다.** 탐색과 검증은 같은 데이터 버전을 사용하고, 응답에 그 버전을 표시한다.
6. **결과 상태를 정확히 구분한다.** 최적 / 유효(최적성 미확인) / 보유 데이터 기준 해 없음 / 미확정 / 내부 오류를 섞지 않는다.
7. **허용된 범위에서만 수집·보관한다.** 사용 가능 기간(신선도)과 보관 가능 기간(보관 기한)은 다른 기준이다.
8. **점수는 정의한 것만 보장한다.** 벤치마크는 정의한 점수의 최적화 능력을 측정하며, 실제 경기 품질을 입증하지 않는다.

## 2. 근거와 한계

**읽은 자료**: 저장소 README, velog `Develop_FRS` 7편, 넥슨 오픈 API 게임 페이지, 검토 1(실제 저장소 코드 대조, 공식 메타데이터·약관·상세 페이지 소량 조회 포함), 검토 2(v2와 기존 코드 연결 검토, OR-Tools 공식 문서 대조 포함)

**아직 확인하지 않은 것**
- 오픈 API 키의 실제 호출 유효성 (보유 여부는 사용자 확인), 강화별 급여 규칙의 전체 범위
- 급여·가격·강화 데이터의 지속 수집·이용 허용 범위, 가격 의미·갱신 빈도
- 기본 HTML의 기존 선택자 부재는 회귀 샘플 4건에서 확인. 능력치 별도 응답의 실제 요청은 베컴 강화 1·2단계만 확인
- 동일 인물 중복 배치 규칙, 현재 팀컬러 종류별 전체 조건
- 모델 평가 함수 버그는 합성 입력으로만 확인. 재학습·성능 비교는 하지 않음
- 실데이터 MongoDB 적재, API 서버, LangGraph, 탐색기 소요 시간, 기존 모델의 새 의존성 호환성은 검증하지 않음. Stage 1-0의 기본 모듈 import·합성 DB 적재는 별도 검증 완료

## 5. 착수 전 결정 항목 📌

Git·진행 정책 결정 (2026-10-18): 사용자가 승인된 범위의 PR 자동 병합과 후속 단계 자동 진행을 요청했다. 제품·데이터 정책 등 미결정 항목은 질문하며, 모바일 알림은 앱 지원·연결·설정을 확인한 범위에서만 안내한다. 제품 결정은 사용자 답변을 아래 표에 별도 기록한다.

Stage 1-0 개발 환경 결정 (2026-10-18 사용자 답변):

- Python 3.11.15 + 저장소 `.venv` + pip 사용
- 무작위 User-Agent 제거, HTTP 클라이언트 기본 식별자 사용
- Python 3.11 호환 안정 버전을 검증해 의존성·pytest·Ruff·MongoDB 이미지를 선정·고정

        │
   Agent (LangGraph)                                              ← Stage 4
     ① extract    LLM: 원문에서 조건 구간 추출 (금액은 원문 문자열 그대로)

신선도·갱신·보관을 분리한다 (원칙 7). 시간 필드 공통 규칙 🔶:

| 필드 | 의미 | 결정 근거 |
|---|---|---|
| `observed_at` | 값을 관측한 시각 | 수집 시 기록 |
| `valid_until` | 추천 사용 기한 (이 시각부터 사용 불가). 미확정은 `null`이며 `ok`로 사용할 수 없음 | D8 |
| `delete_after` | 삭제 기한. D2의 무기한 로컬 보관은 `null`로 명시하며, 필드 누락과 구분 | D2 |

| `batch_id` | 같은 수집 배치를 묶는 ID (스냅샷 구성에 사용) | 수집 시 기록 |

추천 사용 시각은 `[observed_at, valid_until)`로 판정하고 기한 이상이면 사용하지 않는다. `valid_until = null`은 신선도 미확정이며 `status = ok`로 기록하지 않는다. `delete_after`가 날짜이면 해당 시각에 삭제하고 `valid_until ≤ delete_after`를 만족해야 한다. `delete_after = null`은 로컬 보관 기한 없음이며 신선도 제한을 없애지 않는다. 이 표현은 사용자 운영 정책을 위한 것이고, 제공자 이용 허용·보관 제한을 확인했다는 뜻이 아니다. 0-B 판정 전 지속·대량 수집 제한은 유지한다.

#### 3-0. 요청별 스냅샷

#### 3-A. scorer — 성능과 배치를 분리
기본 배치의 순수 계약과 합성 52개/전체 685개 검증을 완료했다. [기본 배치 코드](stage-3-a-placement-implementation.md)를 따르며 현재 1-E 검색·스냅샷/solver/API는 변경하지 않았다.
초기 D5 배치는 등록 포지션 계열의 `base`만 사용하고 모델 확장은 끄도록 사용자 확정했다. 기존 제안의 정확 코드 표현과 모델 확장보다 현재 결정을 우선하며 [배치 계약](stage-3-a-placement-contract.md)을 따른다.
사용자의 후속 코드 승인에 따라 성능 부분의 순수 함수와 합성 41개/전체 633개 검증을 완료했다. [성능 코드 기록](stage-3-a-performance-implementation.md)을 따른다. 배치 판정·solver·API 연결·실데이터 점수 실행은 없으며 3-A 전체 완료를 뜻하지 않는다.
2026-10-19 사용자 결정으로 **성능 점수 계약 설계만** 선행했다. [3-A 성능 계약](stage-3-a-performance-contract.md)은 OVR/2·운영 상한 200·점수 키 대응·누락 제외를 기록하며 scorer/solver 구현이나 D5 배치 확장 완료를 뜻하지 않는다.
검토 2 3.2에 따라 두 개념을 분리한다.

| 개념 | 정의 | 신호 | 사용 위치 |
|---|---|---|---|
| **성능** `performance(c, s)` | 카드 c가 자리 s에서 얼마나 뛰어난가 | D7: 포지션별 OVR(0-A9) 또는 포지션 그룹별 능력치 가중합 | 목적함수 |
| **배치 허용** `placement(c, s)` | 카드 c를 자리 s에 놓아도 되는가 | 등록 포지션(기본 허용) + 모델 확률(확장 허용, [실]) | 제약 + 감점 |

- **성능 점수**
  - 0~100 범위로 정규화한다. 가중합을 쓰면 포지션 그룹별 가중치 표를 README에 명시하고, 가중치의 근거(게임 내 포지션 OVR 공식 참고 여부 등 ❓)를 적는다
  - 같은 자리에서 두 카드의 점수 차이가 "더 뛰어남"을 뜻해야 한다. 모델 확률은 여기에 넣지 않는다
- **배치 허용**
  - `base`: 등록 포지션에 자리가 포함되면 허용
  - `extended` [실]: 등록 포지션 밖이지만 모델 확률 ≥ τ이면 허용 + 감점 λ. τ와 λ는 성능 점수와 같은 단위로 정의 🔶
  - 그 외: 배치 불가 (변수를 만들지 않음)
  - [데모]: `base`만 사용하거나, 1-S에서 생성한 "확장 적합" 레이블로 `extended`를 시연 🔶
- 결과 표에 각 선수의 배치 유형(`base` / `extended`)을 표시한다

2026-10-20 승인한 [합성 엔진 계약](stage-3-b-c-engine-contract.md)을 먼저 구현한다. 아래 제안 중 CP-SAT·OVR 정수 목적·정밀도 손실 없는 BP/급여·고정 탐욕 순서와 동일 인물/전원 클럽 자격을 확정했다. DB/실데이터/API·D6 완료는 포함하지 않는다.
- 정식화 🔶
  - 변수: `x[c, s] ∈ {0, 1}`, `placement(c, s)`가 허용인 쌍에만 생성
  - 각 자리 정확히 1명, 각 카드 최대 1자리, 동일 인물 합계 최대 1 (0-C3)
  - Σ 가격 ≤ 예산, Σ 급여 ≤ 급여 상한 (스냅샷 값 사용)
  - 팀컬러 조건 (0-C2, D3)
  - 목적: Σ `performance(c, s)·x[c, s]` − Σ `λ·x[c, s]`(extended 쌍)
- 라이브러리는 D4. CP-SAT을 쓰면 정수 계수가 필요하므로 점수·금액의 스케일링 규칙을 정한다 ❓ (구현 시 공식 문서 확인)
- 시간 제한을 설정값으로 둔다
- 베이스라인 2종 (같은 스냅샷·제약·점수 사용): (1) 자리별 최저가 우선 (2) 자리별 성능 순 탐욕 배치

#### 3-C. validator
같은 스냅샷으로 재검증한다. 초안 (D5에서 확정):

| 대상 | 규칙 |
|---|---|
| 인원 | 정확히 11명, 모든 `spid`·강화 단계가 스냅샷에 존재 |
| 중복 | 같은 `spid` 금지, 동일 인물 규칙 (0-A10, 0-C3) |
| 포메이션 | 자리 구성 일치, 모든 배치가 `placement` 허용 |
| 팀컬러 | 소속 여부 또는 발동 단계 (0-C2, D3) |
| 가격·급여 | 입력값을 믿지 않고 스냅샷 값으로 재계산 |
| 데이터 상태 | 사용한 모든 값이 `status = ok`, `t0` 기준 `valid_until` 이내 |

#### 3-D. 결과 상태
CP-SAT 종료 상태(✅ 검토 2)를 서비스 결과로 매핑한다. 다른 라이브러리를 쓰면 같은 의미의 상태로 매핑한다.

| 탐색기 상태 | 서비스 결과 | 응답 |
|---|---|---|
| `OPTIMAL` | 최적 | validator 통과 후 반환, "최적 확인" |
| `FEASIBLE` | 유효 (최적성 미확인) | validator 통과 후 반환, "최적성 미확인", 상한과의 간극 표시 🔶 |
| `INFEASIBLE` | 보유 데이터 기준 해 없음 | 반환 없음. "조건 자체가 불가능"과 구분해 후보 커버리지 표시 |
| `UNKNOWN` | 미확정 | 반환 없음. "시간 내 해를 찾지도, 없음을 증명하지도 못함" |
| `MODEL_INVALID` | 내부 오류 | 반환 없음. 로그 기록 |

탐색기 호출 전 사전 판정:

| 상황 | 처리 |
|---|---|
| 어떤 자리의 허용 후보가 **0명** | 탐색 없이 "보유 데이터 기준 해 없음" (해당 자리 명시) |
| 어떤 자리의 후보가 적음 (기준값 미만) | **실패가 아님**. 탐색은 진행하고 "커버리지 경고"를 함께 반환. [실]은 1-D 보강 목록에 기록 |
| 조건에 맞는 카드는 있으나 가격·급여가 `stale`·`unknown` | "데이터 누락·만료"로 별도 표시. 해당 카드 제외 후 탐색 진행 여부는 설정값 🔶 |
| validator 불통과 (탐색 결과인데 위반) | 내부 오류로 처리하고 반환하지 않음. 버그로 기록 |

#### 3-E. 벤치마크

[합성60문제 실행](stage-3-e-benchmark-results.md)에서 유효해45/45·제약107/107·작은최적값15/15·상태180/180·유효탐욕 대비 악화0/62로 D6 기능 기준을 통과했다. 후속003에서 확정한 합성 지연 p95≤1초를 통과했으며 로컬 CP-SAT 스냅샷 포함 p50/p95=24.2/194.0ms를 관측했다. DB/실데이터/운영 성능의 검증은 아니다.

2026-10-20 사용자 결정으로 [합성 벤치마크 계약](stage-3-e-benchmark-contract.md)의 60문제/시드123/후보3·10·30 및 D6 초기 수치를 확정했다. 아래 제안 중 채택 범위와 아직 미정인 지연 목표/실데이터 검증을 구분한다.
이 벤치마크는 **정의한 점수를 얼마나 잘 최적화하는지** 측정한다. 실제 경기 품질의 입증이 아니다 (원칙 8).

**문제 생성** 🔶
- 해 존재 문제: 스냅샷에서 유효 스쿼드를 하나 구성하고 **먼저 validator로 검증**한 뒤, 그 합계에 예산 여유(예: 0%, 5%, 20%)를 더해 조건을 만든다
- 난이도 분산: 예산 여유 × 후보 수(자리당 적음 / 보통 / 많음) × 팀컬러 조건 유무
- 해 없음 문제: 최저 비용 조합보다 작은 예산, 후보 0명인 자리 등
- 소규모 문제: 후보를 줄여 **전수 탐색으로 최적값을 구할 수 있는** 문제 세트

**측정 항목과 초안 기준** (D6에서 확정)

| 항목 | 내용 | 초안 기준 🔶 |
|---|---|---|
| 유효해 반환율 | 해 존재 문제에서 `OPTIMAL` 또는 `FEASIBLE`을 반환한 비율. 방법별(엔진·베이스라인)로 측정 | 엔진 ≥ 95% |
| 전체 제약 준수 | 반환된 모든 스쿼드가 3-C 통과 | 100% |
| 최적성 대조 | 소규모 세트에서 `OPTIMAL` 결과가 전수 탐색 최적값과 일치 | 100% |
| 베이스라인 비교 | 같은 문제에서 동점 / 개선 / 악화 비율 기록 | `OPTIMAL` 결과의 악화 0% (악화가 있으면 버그). 개선 비율은 기록만 |
| 최적성 간극 | `FEASIBLE` 결과의 상한 대비 간극 | 분포 기록 |
| 상태 보고 정확도 | 해 없음 문제에서 `OPTIMAL`·`FEASIBLE`을 반환하지 않음. `INFEASIBLE`과 `UNKNOWN` 비율을 기록 | 해 없음 문제의 해 반환 0% |
| 지연시간 | 문제 규모별 p50·p95 | 첫 측정 후 정함 ❓ |

쉬운 문제에서 베이스라인과 동점인 것은 정상이다. 동점이 많다면 그 자체를 결과로 기록한다.

### Stage 4 — Agent (MVP 종점)

**선행**: Stage 3
**먼저 결정할 것** ❓: LLM 공급자·모델(공식 문서로 현재 모델명·가격·한도 확인), LangGraph 현재 API

#### 4-A. 조건 추출과 정규화

[필수 5조건 정규화 코드](stage-4-a-conditions-implementation.md)는 후속 승인으로 수동/합성 근거만 정규화한다. 강화 문법/급여/정식값·누락/미지원/충돌 보고를 새120/전체1051개 테스트로 확인했다. LLM 추출·DB/API·실제 스쿼드 실행과 의미/E2E 평가는 포함하지 않는다.

[원문 구간·정확 금액 코드](stage-4-a-amount-implementation.md)는 후속 승인 범위로 구현했고 합성92/전체931개·Ruff·환경/pip 검증을 통과했다. 전체 조건 조립·강화/별칭·LLM/API는 포함하지 않는다.

2026-10-20 [정규화 계약 설계](stage-4-a-normalization-contract.md)를 코드/LLM 없이 선행했다. 필수5조건·누락/미지원/금액 모호성 처리와 정확 BP 변환의 사용자 결정 및 구현 전 제안을 구분한다. 코드/유료 호출·1-D/F 선행 완료는 아니다.
- **extract (LLM)**: 원문에서 조건 구간을 추출한다. 금액은 원문 문자열 그대로(`"1조 5천억"`) 반환하고 숫자로 바꾸지 않는다
- **normalize (코드)**
  - 한국어 금액 파서로 단위를 변환한다 (`억`, `조`, `경` 등). 파서는 단위 테스트로 검증한다
  - 추출한 구간이 원문에 실제로 존재하는지 문자열 대조한다 (원문에 없는 조건 생성 방지)
  - 필수 조건이 빠지면 되묻는다
- **지원 범위 밖 조건**
  - 미지원 팀컬러·포메이션·강화 단계는 비슷한 것으로 **임의 대체하지 않는다**
  - "지원하지 않는 조건"으로 응답하고 지원 목록을 함께 보여준다
- 스키마 검증(Pydantic 통과)과 의미 정확성(원문 의도와 일치)은 다른 단계로 취급한다

#### 4-B. build

[수동/합성 연결 코드](stage-4-b-build-implementation.md)는 정규화 오류 시 자료/엔진을 사용하지 않고, 정상일 때만 명시 배치·시각의 메모리 스냅샷을 기존 CP-SAT/독립 검증과 연결한다. 새46/전체1097개 합성 테스트·Ruff 등을 통과했다. 실제 LLM·DB/API·실데이터 실행과 4-D 평가는 포함하지 않는다.
Stage 3 엔진 호출. LLM은 선수를 고르지 않는다.

#### 4-C. render + narrate + check
- **render (코드)**: 보장해야 하는 항목은 코드가 표로 출력한다 — 선수명, 자리, 배치 유형, 강화 단계, 가격, 급여, 합계, 결과 상태, 스냅샷 시각
- **narrate (LLM)**: 입력은 확정 JSON과 **허용 근거 필드**(성능 점수 구성 요소, 배치 유형, 조건 대비 여유 등)뿐이다. 서술은 표를 보충하는 용도이며 표의 숫자를 다시 쓸 필요가 없다
- **check (코드)**: 검출 범위를 다음과 같이 정한다

| 구분 | 내용 | 처리 |
|---|---|---|
| 검출 가능 | 확정 JSON에 없는 선수명 / JSON과 다른 강화 단계·금액·합계 / JSON에 없는 수치 | 재생성, 반복 실패 시 템플릿 서술 |
| 부분 검출 | 근거 필드와 연결되는 비교 주장(예: "이 자리에서 성능 점수가 가장 높음") — 해당 필드 값으로 대조 | 대조 실패 시 재생성 |
| 검출 불가 | 근거 필드와 연결되지 않는 평가 주장(예: "가장 빠르다", "최고의 가성비") | 프롬프트로 금지 + 금지 표현 목록으로 1차 차단. 잔여 위험으로 문서화 |

#### 4-D. 평가
후속 사용자 승인으로 [W6 평가 코드](stage-w6-evaluation-implementation.md)를 구현했다. 정답 선택 대역25/25·사전 해 존재8/해없음3 증명·신규61/전체pytest1,553개·Ruff 통과다. 이후 [실모델 평가](stage-w6-model-evaluation.md)는 모델 대상근거/의미15/16·전체E2E24/25였다. 정상8/8과 M02 선택 오류를 구분하고 실제 지연·토큰·실패를 기록했다. 대역/실모델 초기 실패 원본을 모두 보존한다.
