# 추천 급여 상한 310 고정

2026-10-22 사용자 결정. 사용자가 현재 게임의 상한이310이라고 확인했고, 후속 답변으로 **항상310: 생략하면 자동 적용, 다른 급여를 입력하면310 고정 안내 후 수정 요청**을 선택했다. 공식 사이트를 새로 조회한 사실로 기록하지 않는다.

## 새 요청의 규칙

- 실데이터 브랜치의 웹/API 추천과 MCP 추천은 시스템 급여 상한310을 적용한다. 낮은 상한도 별도로 받지 않는다. 합계가 정확히310이어야 한다는 뜻은 아니며, 검증된11명의 급여 합계가310 이하여야 한다.
- 사용자가 입력해야 하는 조건은 예산·클럽·포메이션·허용 강화 네 가지다. 급여 생략은 오류가 아니며310을 적용한다. 정규화 결과와 스냅샷/응답에는 `salary_cap=310`을 명시한다.
- 명시한 급여의 정상 정수값이310이면 허용한다. 0·200·300·311 등 다른 값은 `fixed_salary_cap` 사유와310 고정 안내를 반환하고 모델/자료/엔진에 도달하지 않는다. 서로 다른 급여를 마지막 값으로 선택하거나 조용히 덮어쓰지 않는다. 기존 잘못된 문법/원문 구간 오류도 유지한다.
- 생략한 급여의 원문 근거를 만들어 넣지 않는다. `evidence.salary_cap`은 빈 목록이며310은 사용자 확정 시스템 규칙에서 온다. 모델은 원문에 있는 ID만 고르며 없는 급여 ID를 생성하거나 입력문을 바꾸지 않는다.
- 나머지 조건의 누락·미지원·예산 충돌은 기존처럼 명확화하며 자료 접근 전에 중단한다. 명시 배치·스냅샷·CP-SAT·독립 검증·만료를 유지한다. 원래 선수별 급여 관측을310으로 변경하지 않는다.

## 적용·버전·보존

새 사용자 경로가 고정 정책을 명시적으로 주입하며, HTTP/환경 설정으로 이전 급여 규칙을 선택하는 옵션은 제공하지 않는다. 순수 엔진/정규화·벤치마크와 과거 오프라인 평가 재현에 필요한 기존 명시 급여 계약은 내부에서 유지한다. 기존 평가25문장·사전 정답·실측24/25·과거 E2E/DB 검증·원본/완료 manifest·잠금을 새 정답으로 덮어쓰지 않는다.

웹은 “급여 상한310 고정·입력 생략 가능”을 안내하고 예시에서 임의 급여를 제거한다. 성공 응답의 급여 상한/합계를 서버 값 그대로 표시한다. 웹/서버 모의 fixture는 새 동작으로 재생성하되 모두 합성 선수/수치만 쓴다. 다른 담당의 활성 웹/자료 체크아웃은 수정하지 않는다. master/develop의 합성v0와 실행 중5173을 보존하며 `feat/real-data`만 대상으로 한다.

## 구현·합성 검증 (INT-RD-008)

계약 PR#115를 `feat/real-data`에 병합한 뒤 별도 기능 PR에서 구현했다. API의 `AgentService.fixed_salary_cap`은 생성 인자로 바꿀 수 없는 불변310이고, MCP도310을 직접 주입한다. 환경/HTTP의 해제 옵션은 없다. 내부 순수 함수의 `fixed_salary_cap=None`은 기존 명시 급여·오프라인 평가 재현 경로이며 새 서비스가 사용하지 않는다. 후보 registry·ID 해시에 정책을 결합하고, 근거 복원/그래프/요청 build/웹 재검증까지 같은 정책을 전달한다.

누락한 급여는 근거를 만들지 않고310을 적용하며, 명시 급여 불일치는 `prepare.fixed_salary_cap`(unsupported)로 모델/요청 자료/엔진 전에 차단한다. 기존 bad syntax·원문 불일치·예산/다른 조건 사유를 유지한다. 정규화·후보/그래프 버전을 정책별로 구분하며 기존 내부 정규화 해시 `c83756caefaa6c33bee73d5b5c8b57ac1646187d6d4d5b446e93147054763e33`도 회귀 검증했다. 모델 ID 배열 형식/웹 필드 구조·SSE/health 버전은 같다.
