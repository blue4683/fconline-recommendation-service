# MF-3 필드 우선·GK 단계·다요소 보조 목적 계약

2026-10-23 사용자 결정. 기준 develop `92b5ec2`. [MF-3 영향 분석](multi-factor-integration-impact.md)의 MF3-D1~D6 중 이번에 확정한 범위와 구현 계약을 기록한다. [MF-2 파일럿 결과](multi-factor-preference-pilot.md#7-실제-평가-결과-2026-10-23)는 OVR 차이 ≤ 2인 카드 쌍에서만 측정했으므로, 다요소 점수는 **OVR이 거의 같은 해들 사이의 보조 기준**으로만 쓴다.

## 1. 사용자 결정

| 항목 | 결정 |
|---|---|
| 역할 | OVR이 주 기준이다. OVR이 허용폭 안에서 비슷한 해들 중에서만 다요소 점수가 높은 해를 고른다 |
| 골키퍼 | 사용자의 실제 운용("필드에 급여를 먼저 쓰고 남은 급여로 GK")을 반영해 필드 10명과 GK를 단계로 나눈다. 슬롯 가중치는 두지 않는다 |
| 허용폭 | 필드 10명 OVR 합 **−5**, GK OVR **−2** |
| 예산 동점 | 기존 [OVR 동점 예산 활용](budget-tiebreak-contract.md)을 마지막 단계로 유지한다 |
| 적용 범위 | 스냅샷·CP-SAT·독립 검증·합성 검증까지. HTTP/SSE·MCP·웹의 `web-agent.v1`/`mcp-build.v1`은 변경하지 않는다 |
| 기본값 | 명시 선택 시에만 동작한다. 기존 OVR 모드가 기본이며 그 스냅샷·엔진 사양·결과는 바뀌지 않는다 |

권장안으로 함께 확정한 전제(MF3-D1·D2): 정책은 호출자가 명시한 `ScoringPolicy`와 기대 해시를 쓴다. 현재 검증 대상은 `draft-core-stat-foot-20261022`(experimental)이며 운영 승격이 아니다. OVR이 없는 후보는 지금처럼 제외한다.

## 2. 목적 (objective `gk_priority_multi_factor`)

F = 필드 10개 슬롯의 `raw_ovr` 합, G = GK 슬롯의 `raw_ovr`, M = 11명의 다요소 `score_units` 합(1unit = 0.01점, GK는 정책의 gk 프로필), P = 총 가격이다.

1. **S1** F 최대화 → F*.
2. **S2** F = F*로 고정하고 G 최대화 → G*. 필드 OVR을 먼저 확보한 뒤 남은 급여·예산으로 GK를 고른다.
3. **S3** F = F* 고정을 풀고 F ≥ F* − 5, G ≥ G* − 2 범위에서 M 최대화 → M*.
4. **S4** M = M*로 고정하고 P 최대화(기존 정확 BP 방식).

- 기존 11명 슬롯·카드/인물 중복 금지·클럽 자격·허용 강화·기본 배치·예산/급여 정확 상한 제약은 그대로다. 목적들을 큰 계수 하나로 합치지 않는다.
- S3에서 G는 하한만 있으므로 필드가 허용폭 안에서 낮아져 GK가 G*보다 좋아지는 해도 허용된다. 이 경우에도 F ≥ F* − 5를 넘지 않는다.
- M은 카드마다 MF-1이 양자화한 `score_units`의 정수 합이다. 역할 간 점수 교정은 하지 않았으며 MF-2에서 검증한 범위도 아니다.

## 3. 상태·시간

- 네 단계가 기존 최대 10초·1스레드·시드 123을 공유한다. 단계마다 시간을 새로 배정하지 않는다.
- 한 단계가 최적을 증명하지 못하면 그 단계까지 찾은 가장 좋은 유효해를 유지하고 뒤 단계는 `not_run`이다. 각 단계의 시작 해는 앞 단계 해이므로, 단계 목적값이 시작 해보다 나빠지는 해로 바꾸지 않는다.
- `EngineResult.status=optimal`은 S1~S3이 모두 최적일 때만이다. 그 밖의 유효해는 `feasible`이다. S4는 기존 `price_optimization_status`로 따로 보고한다. 단계별 상태와 값은 `objective_stages`에 남긴다.
- 기존 `best_bound`/`absolute_gap`은 OVR 단일 목적의 단위라 이 모드에서는 `None`이다.
- 탐욕 비교 두 방식은 기존 OVR·가격 순서 그대로이며 이 목적을 따르지 않는다.

## 4. 스냅샷·검증

- 스냅샷 메타데이터에 목적 사양(모드·허용폭·단계 순서)과 정책 원문·버전을 고정하고 `snapshot_id`에 반영한다. 정책 없이 만든 스냅샷은 지금과 바이트 단위로 같다.
- 후보마다 다요소 점수를 계산해 `score_units`와 입력 해시를 보존한다. 다요소 계산에서 제외된 카드·강화·슬롯은 `resource=multi_factor`와 MF-1 사유로 제외 목록에 남기며, OVR로 대신하지 않는다. 제외 후보의 관측은 기한 계산에 넣지 않는다.
- 독립 검증은 스냅샷의 정책 원문으로 점수를 원관측에서 다시 계산해 대조하고 11명의 `score_units` 합을 보고한다. 단계 최적성은 검증기의 범위가 아니며, 작은 합성 문제의 전수 탐색으로 따로 대조한다.
- 출력·Agent 경로는 이 모드의 결과를 받지 않는다. 기존 문구("동일 OVR")와 v1 DTO는 OVR 모드 전용이다.

## 5. 검증 계획과 미실행

- 합성 단위 검증: 단계별 우선순위(필드 OVR 1 우선, 필드 동점에서 GK 우선, 허용폭 경계 −5/−6·−2/−3, 허용폭 안 다요소 선택, 다요소 동점 내 최대 사용액), 기존 OVR 모드 스냅샷/결과 불변, 점수 변조·정책 해시 불일치 거부, 다요소 제외 사유·기한, 시간 미확정 단계 처리.
- 작은 무작위 합성 문제 전수 탐색과의 사전식 최적값 대조.
- 필수 `pytest`·Ruff lint/format.
- 실제 관측 파일로 OVR 모드와 비교하는 오프라인 실행, API/웹 노출, 기본 모드 변경, 정책 가중치 조정은 이번 범위가 아니다. 새 수집·모델 호출·DB 쓰기·배포도 없다.

## 6. 구현 결과 (2026-10-23)

- `FRS/core/squad_recommend/objective.py`: `MultiFactorObjective`(정책 원문+기대 해시), `objective_spec`(모드·허용폭·단계·정책 원문을 해시). `build_snapshot(..., objective=)`·`build_squad_request(..., objective=)`로만 선택한다.
- 스냅샷: 다요소 제외는 `resource=multi_factor`로 남기고 후보·기한에서 뺀다. 후보에 `score_units`·`score_input_version`, 메타데이터에 `objective`를 둔다. 정책이 없으면 키를 추가하지 않는다.
- 검증기: 메타데이터의 정책 원문으로 목적 사양을 재구성해 대조(`objective_mismatch`)하고, 후보 점수를 원관측에서 다시 계산(`multi_factor_mismatch`)한다. 유효 결과에 선수별 `score_units`와 `total_score_units`를 보고한다.
- 탐색기: `_base_model`로 공통 제약을 만들고 단계마다 새 모델에 앞 단계 제약을 더한다. 가격 단계는 기존 `_maximize_price`를 그대로 쓰며, OVR 고정 제약은 호출자로 옮겼다(제약 추가 순서 동일). 엔진 사양은 `gk_priority_engine_spec`으로 분리했다. `EngineResult.objective`·`objective_stages`를 추가했다.
- OVR 모드 보존: 새 필드는 기본값일 때 직렬화에서 빠진다. 기존 스냅샷 bytes·`engine_spec`·결과 dump·v1 DTO가 그대로이며, 코드 출력은 OVR 이외 목적을 내부 오류로 거부한다.
- 검증: 신규 합성 32개(우선순위·허용폭 경계·GK 남은 급여·같은 점수 내 사용액·제외/기한·변조 4종·버전 불일치·단계 미확정 3종·시간 공유·탐욕/만료 표시·무작위 12문제 전수 대조). 무작위 12문제 중 11문제에서 허용폭 안 다른 해가 선택되어 S3이 실제로 작동했다. 전체 pytest 2,145개·Ruff lint/format 288파일 통과. 기존 D6 60문제 벤치마크는 OVR 경로 코드가 바뀌지 않아 재실행하지 않았다.
- 미실행: 실제 관측 파일 비교, 다요소 모드 지연 측정, API/웹/MCP 노출.
