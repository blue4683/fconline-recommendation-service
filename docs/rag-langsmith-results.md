## LangSmith 수신과 전송 내용

사용자가 지정한 Git 제외 `.env`를 읽기만 했다. 미국 endpoint의 **FRS** 프로젝트에 **POST26/상한28 + GET1/상한1**, 합계27요청을 보냈다. 모든 POST는 성공 응답을 받았고 첫 root의 GET은 HTTP200·동일 run ID로 수신을 확인했다. 구성은 root7/retrieve7/generate6/validate6이다. 26개 전체의 UI 표시나 검색 가능 상태를 각각 조회한 것은 아니다.

원문·답변·검색 본문은 로컬에만 보관했다. SDK 전송 직전 검증한 입력/출력은 `{}`이며, UUID/부모 관계·단계명·시각/지연·상태/안전한 오류 코드·제공 토큰·corpus 해시/생성기 종류·프로젝트명만 보냈다. API 키는 인증 헤더에만 사용했다. 저장된 26개 미리보기를 닫힌 스키마로 재검증해 일치함을 확인했다. `.env`·키·실제 모델 원문·실제 trace payload는 커밋하지 않는다.

K03은 실행 오류가 아닌 답변 누락이므로 trace의 도메인 상태는 `insufficient_evidence`다. K05는 출력 계약 위반이어서 root/validate에 `invalid_output` 오류가 남는다. trace가 기술적으로 성공했다는 사실은 Q&A 정답 통과와 다르다. LangSmith 보관·계정 비용은 로컬 D2와 별개다.

## 실패 분석

**K03:** 정답 구간 `support/required-conditions`가 검색1위였고, 다섯 조건을 모두 담은 본문을 모델 입력으로 전달했다. 모델이 근거 부족을 반환했으므로 이 사례는 검색 누락보다 생성 단계의 불필요한 답변 거절로 분류한다. 왜 거절했는지 내부 원인은 이번 기록만으로 단정하지 않는다.

**K05:** 모델은 근거 부족/빈 답변을 선택했지만 출처 ID 두 개를 함께 반환했다. 확정 계약은 근거 부족이면 `answer=''`·`source_ids=[]`다. 검증기가 이를 수정/삭제해서 성공으로 만들지 않고 안전한 `provider_error/invalid_output`으로 처리했다. 시세를 지어내지는 않았지만 기대한 근거 부족 응답 형식에는 실패했다.

측정 뒤 프롬프트·정답·문서·코드를 바꾸어 재호출하지 않았다. 개선하려면 근거가 있는 질문의 답변 누락과 상태별 출력 일관성을 각각 다루고, 별도 질문/새 승인으로 평가해야 한다. 현재의 실패2건을 그대로 보존한다.
