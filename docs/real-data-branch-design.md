# 실데이터 브랜치 설계 — master는 합성, `feat/real-data`에서 실데이터 수집·사용

작성일: 2026-10-21. 기준 develop `4711d8f`. 작성: 웹 담당. 사용자가 이 문서의 작성과 PR을 직접 요청했다. 평소 웹 담당은 설계 문서를 쓰지 않으므로, 이 문서는 **새 파일 하나와 WEB-007 기록만** 추가한다. 기존 설계도·AGENTS.md·코드·테스트는 바꾸지 않는다. 구현 담당과 실행 승인은 §9에 정리했다. 이 문서는 수집 실행 승인이 아니다.

## 1. 목표

- **master와 develop**: 지금처럼 합성 자료만으로 실행된다. 실데이터 코드·자료·설정을 넣지 않는다.
- **`feat/real-data`**: develop에서 만든 장기 브랜치다. 여기서 넥슨 공식 데이터센터의 실데이터를 수집하고, 같은 Agent·엔진·웹으로 추천한다.
- 두 경로는 엔진(정규화·스냅샷·CP-SAT·독립 검증·만료)을 그대로 공유한다. 바뀌는 것은 자료 공급과 표시뿐이다.

## 3. 브랜치 전략

```text
master ── develop ──────────────┬──────────── (합성 경로 개발 계속)
                                │  정기적으로 develop → feat/real-data 병합
                                └── feat/real-data ── 작업 PR들 (실데이터 수집·공급기·계약·웹)
```

| 규칙 | 내용 |
|---|---|
| 생성 | develop 최신에서 `feat/real-data`를 만든다. 통합 담당이 만든다. |
| 작업 PR | `feat/real-data`를 대상으로 한다. 예: `feat/real-data-catalog`, `feat/real-data-provider`, `feat/real-data-web`. 병합은 통합 담당이 한다. |
| 동기화 | develop의 변경을 `feat/real-data`로 정기 병합한다. 반대 방향 자동 병합은 없다. |
| develop·master 반영 | 기본적으로 하지 않는다. 합성 경로에도 쓸모 있는 일반 개선(예: 200장 상한 분할 함수, 파서 수정)만 따로 PR로 develop에 올린다. 그때도 기본값은 합성이어야 하고 실데이터 자료·설정은 들어가지 않는다. |
| 자료 | 원본·가공 자료는 지금처럼 Git 제외 `data/raw/`, `data/processed/`에만 둔다(`.gitignore` 168행). 실제 선수명·가격을 커밋하지 않는다. 테스트는 합성 응답만 쓴다. |
| CI | 브랜치에서도 기존 Python CI를 그대로 통과해야 한다. 네트워크 요청이 있는 테스트는 없다. |

## 4. 수집 설계

### 4.1 카드 목록 — 클럽 경력 검색을 조건별로 나눠 받기

- 경로: `POST https://fconline.nexon.com/datacenter/PlayerList` ([선수 검색 경로 평가](stage-1-d-search-feasibility.md)에서 200 응답을 확인한 유일한 목록 경로).
- 조건: 클럽 선택(`n4LeagueId`·`n4TeamId`), **클럽 경력 포함**(`n1History=0`, 체크 시 0), `n1Strong=5`, 급여 하한·상한(`n4SalaryMin`·`n4SalaryMax`). 리버풀은 리그 13·클럽 9로 확인됐다. 첼시·바이에른 뮌헨의 리그·클럽 ID는 실행 전에 공식 검색 화면의 `SetAbilitySearch(...)` 값을 읽어 고정한다. 추측하지 않는다.
- **응답 1회당 200장이 상한이다.** 기존 진단에서 2페이지 요청이 1페이지와 같은 바이트를 돌려줬다. 페이지 넘김은 쓰지 않고 조건을 나눈다.
- 기본 정렬이 OVR 높은 순이라, 잘린 응답에서 빠지는 쪽은 OVR이 낮은 카드다. 예산이 빠듯한 요청일수록 이 카드가 필요하므로 잘림을 반드시 찾아내야 한다.

분할 규칙:

1. 시작 칸은 클럽 3 × 급여 구간 5(4~20, 21~25, 26~30, 31~35, 36~99)다. 기존 `BANDS`와 같다.
2. 응답이 **정확히 200장**이면 잘렸을 수 있다고 본다. 그 칸만 급여 범위를 반으로 나눠 다시 검색한다. 급여 한 값까지 나눠도 200장이면 포지션 필터로 나눈다.
3. 포지션 필터 필드는 저장된 공식 검색 폼(`form1`, 컨트롤 60개)에서 이름과 값을 확인한 뒤에만 쓴다. 확인 전에는 쓰지 않는다.
4. 200장 미만인 칸은 그 칸의 전체로 본다. 같은 카드가 여러 칸에 나오면 spid로 한 번만 센다.
5. 나눈 순서와 응답 수를 manifest에 남겨, 어느 칸이 왜 나뉘었는지 재현할 수 있게 한다.

목록 한 줄에서 얻는 것: spid·이름·시즌, 요청 강화의 급여, 표시 포지션 OVR, 선택 능력치 4개, **5~11강 표시 가격 7개**(`span_bp5~bp11`). 가격은 [관측 계약](stage-1-f-observation-policy.md)대로 참고가격이며 0·누락은 unknown이다.

### 4.2 카드 능력치 — 카드당 1회

- `POST https://fconline.nexon.com/datacenter/PlayerAbility`를 카드당 **5강 1회**만 요청한다. 34개 능력치·등록 포지션·포지션별 OVR·급여를 기존 [능력치 파서](stage-1-b-parser-pilot.md)로 읽는다.
- 6~11강 능력치와 OVR은 [강화 파생 계약](reinforcement-derivation-contract.md)의 누적 보너스로 계산한다. 기존 1-B·1-D 두 배치의 5→6~11강 차이 능력치 74,052개·OVR 34,848개가 이 표와 모두 일치했다.
- 기존 계획(259장 × 7강 = 1,813회)보다 요청이 약 7분의 1로 준다.

### 4.3 급여 — 5강 값과 강화별 동일성 확인

- 급여는 5강 목록 값을 쓴다. 기존 표본 200장에서 5강과 11강 급여가 모두 같았지만 일반 규칙으로 확정하지 않았다.
- 그래서 실행마다 클럽당 1회씩 같은 조건의 **11강 목록**을 받아 급여가 같은지 대조한다(3회). 하나라도 다르면 그 실행을 멈추고, 강화별 급여 수집으로 설계를 바꾼다. 다른 값으로 대체하지 않는다.

### 4.4 대조 — 상세 팝업

- 공식 팀컬러 페이지의 상세 버튼 `DataCenter.GetTeamColorDetail(<teamcolorid>)`(리버풀 1001·첼시 1003·뮌헨 1010)은 사용자 브라우저에서 소속 선수를 보여 준다. 한 번에 보이는 수가 정해져 있다.
- 실행마다 클럽당 1회 열어, 표시된 카드가 §4.1 결과에 모두 있는지만 확인한다. 전체 명단의 근거로는 쓰지 않는다.
- 이전에 직접 HTTP로 상세를 요청했을 때 302였다([재진단](stage-1-d-reinspection.md)). 대조는 정상 브라우저에서 사람이 확인하거나, 브라우저가 보낸 요청 계약을 먼저 기록한 뒤에만 자동화한다.

### 4.5 요청 수와 실행 조건

| 단계 | 요청 | 예상 |
|---|---|---:|
| 목록 | 15칸 + 200장 칸 분할 | 15~60 |
| 급여 대조 | 클럽별 11강 목록 | 3 |
| 능력치 | 고유 카드당 5강 1회 | 카드 수 (수백 장) |

- 실행마다 새 `--run-id`와 정확한 `--max-attempts`를 정해 사용자 승인을 받는다. 기존 실행의 남은 횟수는 쓰지 않는다.
- 초당 최대 1회 순차 요청, 재시도 0회. 302/403/429·연결 오류·30초 초과·파싱 실패·관측 충돌이면 즉시 멈춘다. 멈춘 실행은 재개하지 않는다.
- 카드 500장 기준 약 10분이다. 가격 유효 기간이 24시간이라, 시연에 쓰려면 시연 24시간 안에 실행한다.

## 5. 자료 계약

- 기존 스키마(`PlayerCard`, `CardPrice`, `CardSalary`, `ReinforceStats`, `TeamColor`)와 배치 ID·관측 시각·원본 SHA256·출처를 그대로 쓴다. [파생 갱신](stage-1-f-manual-refresh.md)처럼 새 batch_id로만 저장하고 기존 배치를 덮어쓰지 않는다.
- 클럽 자격(`TeamColor`) 관측의 근거 값으로 `club_career_search`를 추가한다(RD-1). 응답에 포함된 카드만 자격이 있고, 응답에 없다는 이유로 자격 없음을 만들지 않는다.
- 유효 기간은 [D8](stage-1-f-freshness-policy.md) 그대로다(가격 24시간, 급여·능력치·자격 7일). 만료된 자료는 엔진이 지금처럼 거절한다. 기간을 늘리지 않는다.
- 팀컬러 발동 보너스는 이번 범위에서 점수에 넣지 않는다. 클럽별 최고 단계·보너스는 공식 팀컬러 목록에서 확인할 수 있으나(사용자 확인, 2026-10-21) 발동 인원 규칙이 미확정이다.

## 6. Agent·API 연결 (통합 담당)

- `MaterialProvider` 프로토콜(`FRS/agent/material.py`)을 따르는 실데이터 공급기를 추가한다. 명시한 batch_id 묶음을 `data/processed/`에서 읽고 원본 해시를 검증한다. 최신 배치를 자동으로 고르지 않는다.
- `FRS/api/agent_runtime.py`의 시작 설정에 자료 모드를 추가한다. 이 브랜치의 기본값도 합성이며, 실데이터는 batch_id 묶음을 명시할 때만 켠다.
- `/health`의 `material`에 자료 모드와 batch_id·관측 시각·가장 이른 기한을 보인다.
- 웹 계약: 지금 `data_mode`는 `"synthetic"`만 허용한다(`FRS/api/agent_contract.py` 144행, `frontend/src/contracts/webAgentV0.ts`). 새 값(제안: `"observed"`)은 INT-020 원칙대로 **계약 버전을 올려** 양쪽을 함께 바꾼다(제안: `web-agent.v1`). v0는 master에서 그대로 유지한다.

## 7. 웹 변경 (웹 담당, `feat/real-data`에서만)

- v1 파서: `data_mode`가 `"observed"`일 때도 받는다. 나머지 엄격 검사는 v0와 같다.
- 상단 안내를 자료 모드에 따라 바꾼다. 실데이터면 "넥슨 데이터센터 관측 자료 · 관측 시각 · 참고가격(거래 보장 아님)"을 보인다. 합성이면 지금 문구를 유지한다.
- 서버 상태 표시에 자료 모드와 batch 관측 시각을 보인다. 자료 만료는 지금처럼 보내기를 막는다.
- 대조 fixture는 통합 담당이 만든 v1 앱 코드에서 다시 만든다. 실제 선수명은 fixture에 넣지 않는다(합성 자료로 생성).

## 8. 검증

- 단위 테스트는 합성 응답만 쓴다. 분할 규칙(정확히 200장일 때만 분할, spid 중복 제거), 11강 급여 불일치 시 중단, 파생 6~11강, 공급기의 해시 검증, v1 계약을 확인한다.
- 수집 결과는 기존처럼 네트워크 없는 검증기로 원본 해시·요청 수·간격·재파싱을 대조한다.
- 실제 시연 확인은 별도 승인 범위에서 기존 [브라우저 E2E](agent-browser-e2e.md)와 같은 방식으로 한다.

## 10. 위험과 미해결

- 포지션 필터 필드가 없거나 동작하지 않으면 급여 한 값 칸이 200장을 넘을 때 전체를 받을 수 없다. 그 칸은 "잘림 가능"으로 남기고 추천 결과에 표시한다.
- 클럽 경력 검색이 임대·짧은 소속까지 포함하는지는 확인하지 않았다. RD-1에 따라 포함된 카드는 자격 있음으로 본다.
