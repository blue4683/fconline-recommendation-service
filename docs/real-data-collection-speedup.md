## A — 전송 시작 기준 페이싱

기존 `fetch_url`은 각 시도 전에1초 대기한다. 새 catalog 전송만 `wait_before_attempt` 훅에 단조 시계 페이서를 주입한다. 훅을 지정하지 않는 pilot/enrich/collect/refresh 등의 기본 대기와 오류 처리는 그대로다. `RequestPolicy(request_interval=0)`을 허용하거나 아주 작은 값으로 속이는 방식은 사용하지 않는다.

1. 시도 수 증가와 pending 기록을 먼저 유지한다.
2. `time.monotonic_ns()` 기준 직전 전송 시작에서1,000,000,000ns가 지날 때까지 필요한 시간만 기다린다. sleep이 일찍 반환하면 남은 시간을 다시 확인한다. 첫 요청에는 이전 전송이 없으므로 별도1초 대기는 없다.
3. `Session.request` 호출 직전 UTC와 단조 시각을 기록한다. 이는 애플리케이션의 세션 호출 시작 경계이며 실제 소켓 패킷 송신 시각을 계측한 것은 아니다. 응답·파싱·파일 처리 시간이1초 이내면 다음 대기에 흡수된다.1초를 넘으면 추가 대기를 하지 않는다.
4. 30초 응답 지연 판단은 기존처럼 대기 뒤부터 측정한다. 페이싱 대기 때문에 정상 응답을 지연 오류로 만들지 않는다. 오류·302/403/429·빈 응답은 재시도 없이 중단하고 결과 미상 시도도 상한에서 빼지 않는다.

### 시각 형식과 검증 경계

| 구분 | 기존 형식1 | 새 형식2 |
|---|---|---|
| 식별 | 기존처럼 `timing_version` 없음(또는1) | manifest와 report에 `timing_version=2` |
| `observed_at` | 기존 요청 어댑터 호출 전 시각 그대로 | `sent_at`과 같은 세션 호출 직전 UTC |
| 추가 기록 | 없음 | 각 성공 응답의 `sent_at`, 정수 `send_started_ns` |
| 간격 검사 | 기존 UTC 차이와1ms 허용 오차 유지 | 단조 ns 차이≥1,000,000,000, 허용 오차0 |
| 누락/알 수 없는 버전 | 기존 기록에 새 필드가 섞이면 거부 | 필수 시각 누락·잘못된 값·manifest/report 버전 불일치·알 수 없는 버전 거부 |

기존 검증기는 `1−0.001=0.999초`를 허용했다. 이를 과거 실행에 소급 변경하지 않는다. **새 형식은0.999초와0.999999999초를 모두 거부**하며, 정확히1초는 허용한다. UTC 시계 보정은 전송 간격 판단에 사용하지 않는다. 기존 관측 시각의 실행 시간 내 포함 검사와 자료 기한 규칙은 유지한다. 새 시각 필드를 재생기에 주입해 원본/가공 결과와 요청 기록을 대조하며, 기존 실행은 옛 형식으로 재생한다. 기존 자료의 시각을 새 방식으로 고치지 않는다.

`5531×1.155초≈106.5분 → 5531×1초≈92.2분`은 약13.4% 단축 **추정**이다. 요청 수·응답 지연·파일 처리 시간이 같다는 가정이며 개선 후 실제 성능 측정이 아니다. 세션은 이미 재사용하지만 서버 측 연결 종료 등으로 연결 비용이 항상0이라고 단정할 수 없다. 기록량 증가와 간격 증가의 상관만으로 manifest I/O의 시간 비중을 확정하지 않는다.

## B — 작은 manifest·응답 저널 (설계만, 구현 보류)

append+fsync만 추가해도 manifest의 pending 해제와 한 번에 커밋되지는 않는다. 구현 전 다음 기록 순서와 중간 종료 상태를 고정해야 한다.

1. 시도 번호·누적 상한·pending을 작은 manifest에 원자적으로 교체하고 파일/필요한 디렉터리 내구성을 확보한 뒤 전송한다.
2. 원본 본문을 저장·동기화하고 확정 경로로 바꾼다.
3. 시도 번호·본문 해시·시각을 포함한 응답을 JSONL에 추가·동기화한다.
4. 저널의 확정 경계(바이트 길이·마지막 시도·해시 등)를 기록한 manifest로 교체한 뒤 pending을 해제한다. 완료 표시는 가공 파일/해시와 저널 정합성을 확인한 뒤에만 쓴다.

각 단계 직전/직후 강제 종료를 주입해 불완전한 마지막 줄·누락·중복·순서 변경·고아 본문·저널보다 앞선 manifest·pending이 남은 실행을 검증기가 거부하는지 확인한다. 결과 미상 요청은 상한에 포함한다. 자동 재전송·끝줄 삭제·기록 복구 후 자동 재개를 추가하지 않는다. 읽기 전용 검증기가 불완전한 기록을 정상 완료로 바꾸지 않는다.

버전별 reader를 분리해 기존 내장 `responses` 형식과 새 저널 형식을 모두 읽되, 새 형식에서 저널이 없다고 옛 형식으로 우회하지 않는다. **현재 `ObservedMaterial`과 `load_observed`는 raw manifest의 responses를 직접 읽지 않고 가공 파일·report를 읽는다.** 따라서 우선 변경 대상은 수집 기록·검증기·재생기이며, 가공/report 계약이 같으면 공급기·DB 적재기는 수정 대신 회귀 검증으로 확인할 수 있다. 실제로 바뀌는 계약을 확인한 뒤 영향 범위를 정한다.

효과는 아직 미측정이다. A 뒤 작은 합성 기록으로 기록 비용·파일 크기·분포를 측정하고 B의 필요성을 판단한다. 진행 중인 실제 자료나 수집 저장 장치에 대규모 I/O 벤치마크를 실행하지 않는다.

## C — 검증된 능력치 재사용 (설계만, 사용자 결정 전 구현하지 않음)

“목록 약86회·약2분”은 **필요한 모든 카드의 능력치가 검증됐고 기한 안이며, 신규·불일치·만료 카드가 없는 경우**에만 가능한 추정이다. 현재 예시의 고유5445장 중 리버풀1634장만 재사용하면 능력치3811장과 목록86회, 약3897회가 남는다(약29.5% 요청 감소). 목록 분할 수·새 카드·응답 지연이 달라지면 횟수와 소요 시간도 바뀐다.

다음 결정은 제안이며 이번 A 구현으로 확정하지 않는다.

- 부모는 완료·오프라인 검증을 통과한 명시 배치만 허용한다. 진행/중단/unknown 자료를 자동 승격하지 않고 최신 배치를 자동 선택하지 않는다. 부모 manifest/가공 해시·원본 관측 키·강화 기준·재사용 규칙·부모 참조를 추적해야 한다.
- 재사용 행의 원래 관측 시각·기한을 유지한다. 새 목록 가격을 받았다는 이유로 능력치의7일 기한을 다시 시작하지 않는다. 추천 스냅샷의 기존 가장 이른 기한 규칙은 완화하지 않는 안을 권장한다.
- 현 공급기는 WEB 출처·단일 실행 배치와 일치하는 행만 받는다. 옛 행의 batch_id만 새 것으로 고쳐 통과시키지 않는다. 자료 종류별 명시 배치 참조나 파생/복합 매니페스트 등 표현 방식과 공급기·DB·독립 검증 범위를 결정해야 한다.
- 신규·만료 카드만 추가 조회할지, 범위 부족으로 중단할지 정해야 한다. 추가 요청은 새 실행의 승인 상한에 미리 포함해야 하며 자동으로 범위를 넓히지 않는다.
- 급여·등록 포지션·OVR 불일치와 게임 업데이트 때의 재사용 중단/새 조회 정책을 정해야 한다. 표시 OVR이 같다고34개 능력치가 모두 같다는 뜻은 아니다. 캐시 무효화 정책과 기존 충돌 중단 규칙을 함께 결정한다.
- 부모 참조 누락·해시 변조·기한 만료·순환 참조·새/옛 관측 충돌을 오프라인으로 검증할 계약이 필요하다. 원래 실행 기록을 덮어쓰지 않는다.
