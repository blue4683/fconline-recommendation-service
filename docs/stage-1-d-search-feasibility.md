# Stage 1-D 선수 검색 경로 활용 가능성 평가

2026-10-19. 사용자가 제공한 선수 검색 경로를 1-D에 활용할 수 있는지 판단해 달라고 요청했다. **새 후보·급여·강화별 표시 가격을 찾는 경로로 활용 가능**하다는 판단이다. 전체 수집·팀컬러 발동 규칙·가격 의미·신선도와 층화 완료는 별도 검증이 필요하며 Stage 1-D는 미완료로 유지한다.

## 범위와 실제 요청

일반 단건·소량 확인 범위에서 새 실행 `stage-1-d-player-search-pilot-20261019`에 HTTP 시도 상한 6회를 설정하고 **실제 5회에서 완료**했다. 기존 stopped 실행은 재개하지 않았다. 기본 UA·초당 최대 1회·재시도/리다이렉트 추적/로그인/출처 위장 없음·오류 즉시 중단·Git 제외 로컬 보관 조건이다. 대량·반복 수집·스케줄러·DB 적재·학습을 실행하지 않았다.

저장된 공식 index HTML의 form1에서 성공한 폼 컨트롤 60개를 읽고, 그 페이지가 참조한 **현재 datacenter.js**를 새로 받아 GetPlayerList의 POST 경로와 폼 직렬화를 확인했다. 오래된 JS만으로 경로를 추측해 요청하지 않았다. 공식 UI의 리그 초기화·클럽 초기화·소속 팀컬러 선택 컨트롤도 대조했다.

| 순서 | 요청·조건 | 결과 |
|---|---|---|
| 1 | 현재 페이지가 참조한 datacenter.js | GET 200, POST /datacenter/PlayerList 확인 |
| 2 | 리버풀 클럽 경력, 5강, 페이지 1 | POST 200, 서로 다른 spid 200개 |
| 3 | 클럽·리그 조건 초기화, 소속 팀컬러 1001, 5강, 페이지 1 | POST 200, 서로 다른 spid 200개 |
| 4 | 같은 소속 팀컬러 조건, 11강, 페이지 1 | POST 200, 같은 spid 200개 |
| 5 | 같은 소속 팀컬러 조건, 5강, 페이지 2 | POST 200, 페이지 1과 동일한 spid 200개·동일한 응답 바이트 |

조건 2는 사용자 URL의 리그 13·클럽 9·n1History=0을 유지하고 n1Strong만 5로 변경했다. 조건 3~5는 공식 UI와 JS를 근거로 n4LeagueId=0, n4TeamId 빈 문자열, teamcolorid=1001, strTeamColorCategory=affiliation을 설정했다. 페이지 번호는 n4PageNo, 강화는 n1Strong으로 전달했다. 다른 검색 제한은 사용자 URL의 폼 값을 유지했다.

공식 JS의 난수 캐시 매개변수는 생략하고 페이지 번호를 별도 정수 문자열로 전송했다. 브라우저의 JavaScript와 jQuery를 실행한 요청을 바이트 단위로 재현한 것은 아니다. 요청 시작 간격의 최솟값은 **1.061274초**였다. 403/429·302·연결 오류는 없었다. 남은 1회를 자동 재사용하지 않고 이번 진단은 종료했다.

## 확보 가능한 필드

검사한 선수 목록 응답마다 200개의 고유한 `area_playerunit_<spid>` 행이 있었다. 각 행에서 다음을 확인했다.

| 자료 | 확인한 범위와 한계 |
|---|---|
| 카드 ID·이름·시즌 표시 | spid를 행 ID에서 읽을 수 있음. 기존 스키마와 결합할 후보 식별자로 사용 가능 |
| 강화 단계 | 행의 Strong<spid> 숨김값과 선택 표시가 요청한 5 또는 11로 일치 |
| 급여 | 200개 행에서 누락 없음. 5강·11강을 비교한 200개 모두 같은 값이었으나 모든 강화·모든 카드의 불변 규칙으로 일반화하지 않음 |
| OVR·표시 포지션 | 표시 포지션과 OVR 존재. 5강→11강에서 200개 모두 OVR가 달라짐. 전체 포지션별 OVR·전체 등록 포지션을 확보한 것은 아님 |
| 능력치 | 이번 폼에서 선택한 속력·가속력·몸싸움·스태미너 4개가 표시됨. 전체 34개 능력치를 대체할 수 없음 |
| 강화별 표시 가격 | 각 행의 span_bp5~span_bp11에 alt/title이 일치하는 양의 절대 정수 BP가 존재. 고유 카드 200개 × 강화 7개 = **1,400개 표시 가격**을 관측. 서로 다른 응답의 같은 카드·강화를 중복 가격 개수로 세지 않음 |

선수 목록의 OVR 열에는 `129 (124)`처럼 기본 OVR를 함께 표시한 값도 있어 전체 텍스트를 정수로 바로 변환하면 안 된다. 표시 포지션 OVR와 괄호의 값을 구분해야 한다. 클럽 경력 토글의 0/1 의미 역시 이전에 확인한 대로 체크 시 0·해제 시 1이다.

## 대조한 사실

- 클럽 경력 5강과 소속 팀컬러 5강의 **이번 응답 200개는 ID와 전체 응답 바이트가 같았다**. 모든 카드·다른 클럽·다른 검색 조건에서 두 필터가 동등하다고 판정하지 않는다. 다른 팀컬러를 이용한 대조는 미실행이다.
- 두 강화 응답은 같은 200개 ID를 반환했다. 5강·11강 표시와 OVR 변경은 확인했지만 6~10강의 능력치 응답은 요청하지 않았다.
- 기존 저장 기본 카드와 겹치는 **12개**를 대조했다. 12개 모두 리버풀 경력이 있었고, 급여·표시 포지션의 등록 여부·해당 포지션 OVR·표시 능력치 4개가 기존 5강 관측과 일치했다. 200개 전체의 과거 원본과 대조한 것은 아니다.
- 응답 5건의 SHA-256을 모두 대조했다. 원본·요청별 전체 폼·집계는 `data/raw/stage-1-d-player-search-pilot-20261019/`에 보관하며 Git에 넣지 않는다.

## 활용 판단과 남은 제한

**활용할 수 있는 부분**은 공식 선수 검색 결과에서 신규 spid를 찾고, 급여와 여러 강화의 표시 가격을 한 응답에서 확보하는 것이다. 소속 팀컬러 검색 조건을 출처와 함께 기록할 수 있어 경력 이력만 사용하던 방식보다 검증할 수 있는 공식 검색 경로가 늘었다. 기존 TeamColorDetail·TeamColorPlayerList를 재호출하지 않고도 선수 검색 결과를 받을 수 있음을 확인했다.

**전체 확보는 아직 보장할 수 없다.** 페이지 1·2가 완전히 같았고 총 개수·페이징 정보가 응답에 없었다. 서버가 모든 상황에서 200개로 제한한다고 단정하지는 않지만, 페이지 번호를 늘리는 것만으로 전체 목록을 모으는 방식은 이번 검사에서 검증되지 않았다. 사용자의 원래 가격·OVR·급여·능력치·신체 조건도 남아 있어 무조건 전체 후보를 반환하는 요청은 아니다.

1-D의 목표는 전체 선수 수 자체가 아니라 등록 포지션 × 급여 구간 × 지원 클럽별 서로 다른 spid 3개다. 후속 수집을 설계한다면 이미 정한 구간으로 나눈 검색이 유력하지만, 필터별 정확한 동작·경계값·중복 제거·빈 결과와 전체 요청 상한을 먼저 검증해야 한다. 필터 분할 수집은 이번에 실행하거나 승인받은 범위가 아니다. 첼시·바이에른 경로도 이번에는 조회하지 않았다.

**스키마에 바로 추천 가능 상태로 적재할 수는 없다.** 목록의 표시 가격이 거래 체결가·구매 가능 가격임을 검증하지 않았고 실제 추천 신선도 D8도 미확정이다. 수집 성공만으로 price_type/status를 임의 승격하지 않는다. 표시 포지션 하나를 전체 등록 포지션으로 바꾸거나 4개 능력치를 34개처럼 취급하지 않는다. 팀컬러 단계별 발동·시즌별 예외·자격의 전체 범위도 별도로 확인해야 한다.

이번에는 경로 활용 가능성을 판단했으며 운영 수집기·가격 파서·새 적재 경로를 구현하지 않았다. 제공자 허용(0-B) 미확정과 기존 외부 수집 제한은 유지한다.

## 검증 기록

공식 HTML·현재 JS·실제 응답·해시·요청 상한/간격·기존 저장 자료와의 12개 교집합을 검사했다. 같은 자료의 중복 집계를 제거했다. 초기 OVR 텍스트에 괄호 값이 있어 전체 문자열 정수 변환을 중단하고 표시 포지션의 별도 정수 노드로 대조했다. 이 형식 차이를 근거로 실제 파서의 경계 사례가 필요함을 기록했다.

저장소 변경은 문서뿐이므로 로컬 pytest·Ruff는 재실행하지 않았다. 실제 HTML·가격·선수별 가공 결과를 fixture나 커밋에 포함하지 않는다. 문서 경로·링크·Git diff를 확인하고 원격 CI는 최신 PR head에서 별도로 확인한다.

## 사용자 제공 PlayerInfo 상세 페이지와 기존 파서 연결

2026-10-19 사용자가 목록에서 선수를 누르면 `/DataCenter/PlayerInfo`에서 구체 정보를 볼 수 있다고 상세 URL을 제공했다. 별도 실행 `stage-1-d-user-player-info-20261019`에서 해당 URL을 **1회 GET하여 HTTP 200**을 확인했다. 기존 완료·중단 실행을 재개하지 않았고 기본 UA·비로그인·리다이렉트/재시도/출처 위장 없음 조건을 유지했다.

대상은 spid=866241084, n1Strong=1이다. 사용자 URL 앞부분의 `8playergrade1min` 표기도 임의로 수정하지 않았다. 이 1강 확인을 MVP 5~11강의 능력치 검증으로 세지 않는다.

초기 HTML에는 클럽 경력 5행이 있었고, 기존 `parse_club_history`로 실제 응답을 읽어 경력 5개와 리버풀 경력을 확인했다. 초기 HTML에서 능력치 파서가 기대하는 34개 행·포지션별 OVR 조각은 없었다. 대신 document ready에서 `DataCenter.GetPlayerAbility(866241084, 1, 0, 0, 0, 0, 0, 0, 0)`을 호출한다. 브라우저 화면의 전체 능력치는 이 추가 로딩과 구분해야 한다.

현재 저장소의 1-B·1-C 구현은 이미 PlayerInfo로 경력을 읽고 PlayerAbility POST로 34개 능력치를 파싱한다. 기존 검증 JS의 GetPlayerAbility 함수도 `/datacenter/PlayerAbility` POST에 spid·강화·적응도·팀컬러 보정 값을 전달한다. 따라서 **새 PlayerList의 spid를 기존 상세·능력치 파서에 연결하는 방식**을 사용할 수 있다. 전체 능력치 조회 기능 자체가 없는 상태는 아니다. 기존 실제 수집은 1-B·1-C 기록에 따른다.

이번 단건 확인에서는 새 PlayerAbility·추가 JS·가격 요청을 보내지 않았으며 34개 능력치를 새로 받은 것으로 보고하지 않는다. 새 카드 수집을 시작하거나 기존 수집 승인을 재사용한 것도 아니다. 선수 목록 200개 밖의 후보 확보·정확한 필터 범위·가격 의미/신선도·팀컬러 발동 규칙 등 앞 절의 제한은 그대로 남는다. 원본·manifest는 Git 제외 로컬에 보관하고 SHA-256·기존 경력 파서 결과·기존 코드의 엔드포인트와 폼·문서 경로를 대조했다.
