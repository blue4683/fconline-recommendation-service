# Stage 2-0 학습 데이터 계약 설계

이 문서는 설계 증분 당시 기록이다. 같은 날 후속 사용자 승인으로 입력 어댑터·피처·라벨·그룹 검증을 구현한다. 현재 완료 범위와 검증은 [입력 계약 구현](stage-2-0-input-contract.md)을 따른다. 공통 변환·출력·매니페스트의 후속 합성 검증은 [산출물 계약 구현](stage-2-0-artifact-contract.md)을 따른다. 아래 미구현 표시는 설계 당시 상태다.

2026-10-19. 사용자는 1-D·1-F를 미완료로 유지하고, 외부 요청 없이 이 계약의 **설계를 먼저 정리**하도록 선택했다. 이 문서는 현재 코드·로컬 관측 사실과 제안·사용자 결정을 구분한다. 어댑터·파이프라인 구현, 데이터 적재, 재학습·평가는 이번 설계 작업에서 실행하지 않는다. Stage 2-0 구현 완료 기준인 계약 테스트도 아직 완료하지 않았다.

## 현재 코드와 자료에서 확인한 사실

| 항목 | 확인 결과 |
|---|---|
| 기존 전처리 | `FRS/core/position_recommend/preprocess.py`는 player_data 문서를 읽고 등록 포지션별 행으로 펼친다. 새 PlayerCard 스키마 어댑터는 없다 |
| 기존 학습 | `model.py`는 전체 자료를 prepare한 뒤 분할한다. 스케일러·체형 인코더·포지션 인코더를 개별 pickle에 저장한다. 새 매니페스트·피처 화이트리스트는 없다 |
| 기존 예측 | `Classifier.predict`는 확률 0.1 이상 클래스의 인덱스 목록을 반환한다. 전체 클래스 확률·model_version을 제공하는 새 계약은 미구현이다 |
| 기존 조회 | `recommend.py`는 player_data.id를 조회한다. 모델 부재 시 학습을 시작할 수 있어 이번 확인에서 호출하지 않았다 |
| 저장 기본 카드 | 서로 다른 spid 1,104개, 모두 기본 5강. 34개 능력치 키가 기존 keyword.json과 일치하며 누락·추가 없음 |
| 부가 정보 | 키·몸무게·체형·개인기·왼발·오른발의 None은 현재 표본에서 각각 0개. 이후 자료의 완전성을 보장하지 않음 |
| 등록 포지션 | 관측된 정규 코드 15종. 복수 등록 카드 523개, 포지션별로 펼치면 1,740행. 28개 Position enum 전체의 학습 자료가 있는 것은 아님 |
| 인물 중복 | person_id 835종, 복수 카드가 있는 인물 172명. 카드 분할과 인물 분할은 다른 평가임 |
| 추천 신선도 | 기본 카드 모두 status=unknown, valid_until=null. 학습 정책 결정과 추천 가능 승격을 구분해야 함 |

입력은 기존 완료 1-B·1-C의 로컬 가공 자료다. 이 자료는 이전 단계에서 원본 대조했으며, 이번에는 PlayerCard 검증과 1-C 완료 manifest의 개별 가공 해시를 대조하고 집계했다. 외부 요청·모델 실행은 없었다. 실제 응답·선수별 레코드를 이 문서나 fixture에 포함하지 않는다.

## 확정된 설계도 요구사항

- `to_model_input(cards) -> DataFrame`으로 새 player_card 계약을 사용한다.
- 피처 이름·순서·자료형을 명시한 feature_spec 화이트리스트를 둔다.
- 학습·추론에서 동일한 변환 객체를 사용하며 추론 피처 불일치를 오류로 처리한다.
- 모델·변환기·인코더·feature_spec·입력 batch_id·라이브러리 버전을 매니페스트로 묶고 그 해시를 model_version으로 쓴다.
- 전체 학습 클래스 확률과 model_version을 반환한다. 기존 임계값 목록 함수와 구분한다.
- 이 모델은 **등록 포지션 분류기**다. D7 성능 점수·D5 좌우 배치 확장·게임 내 팀컬러 자격을 결정하지 않는다.

## 사용자 확정 결정 (2026-10-19)

다음 세 항목은 사용자 답변으로 확정했다. 설계 정책을 확정한 것이며 코드 구현·학습 실행이나 추천 신선도 변경을 뜻하지 않는다.

| 항목 | 사용자 결정 | 상태 |
|---|---|---|
| 피처·누락 처리 | 능력치 34개 + 키·몸무게·체형·개인기·왼발·오른발 6개 = **40개**. 이름·ID·급여·가격·포지션별 OVR·등록 포지션·메타데이터는 X에서 제외하고 필수 피처 누락은 오류 | 확정 |
| 복수 등록 라벨 | **등록 포지션별 학습 행 유지**. 같은 spid의 펼친 행은 함께 분할. 출력은 학습한 전체 클래스의 확률이며 미학습 좌우 슬롯을 임의 확장하지 않음 | 확정 |
| 과거 관측 학습 | **학습 사용과 추천 사용 기준 분리**. 별도로 명시한 완료 배치의 구조·출처·해시가 검증된 과거 관측은 오프라인 학습에 사용할 수 있음. 추천 상태 unknown·valid_until=null은 유지 | 확정 |

과거 관측 사용 정책은 선택 배치의 검증을 생략하는 허가가 아니다. 제공자 허용(0-B)이나 D8의 실제 추천 사용 기간을 확정하지 않으며, 이번 작업은 계약 설계만 하고 학습을 실행하지 않는다.

## 구현을 위한 제안 계약

아래는 확정한 세 정책을 반영한 구현 초안이며 아직 새 코드로 구현하지 않았다. 자료형·직렬화·전처리 등 세부 구현 제안은 사용자 확정 결정과 구분한다.

### 입력과 식별자

호출자가 사용할 완료 배치 ID와 관측 버전을 명시한다. 자동 최신 선택·수집·DB 갱신은 하지 않는다. 인입 어댑터는 PlayerCard 스키마, 배치 포함 여부, spid 중복·충돌, 요청 강화 기준, 피처 완전성을 검사한다. 동일 관측은 중복 제거할 수 있지만 같은 카드의 충돌 버전은 오류로 보고하며 임의 선택하지 않는다.

입력 표는 카드당 한 행이다. spid는 행 식별자로 별도 보존하고, person_id·batch_id·version도 그룹 분할·출처 기록에만 사용한다. 이 정보와 이름·급여·가격·팀컬러·skills·used·관측 시각·유효 기한·등록 포지션·position_ovr는 모델의 X에 넣지 않는다. 등록 포지션은 별도 y다. 좌우 슬롯별 OVR 유무·키를 학습 피처로 변환하지 않는다.

### 확정 피처와 화이트리스트 구현 초안

기존 키 이름을 그대로 사용해 호환성 변경을 분리한다. 특히 `accelartion`, `mid-distance_shot`, `man-to-man_defense`를 임의로 이름 변경하지 않는다.

능력치 34개 순서:

```text
speed, accelartion, goal_determination, shooting_power,
mid-distance_shot, positioning, volley_shot, penalty_kick,
short_pass, field_of_vision, cross, long_pass, free_kick, curve,
dribble, ball_control, agility, balance, reaction_speed,
man-to-man_defense, tackle, intercept, header, sliding_tackle,
struggle, stamina, positiveness, jump, composure,
gk_diving, gk_handling, gk_kick, gk_reaction_speed, gk_positioning
```

확정한 40개 피처를 구성하도록 뒤에 `height, weight, physical, dribble_skill, left_foot, right_foot`을 붙인다. 원시 숫자 열은 int64, physical은 검증한 문자열로 명시하고, 최종 모델 입력은 숫자 변환 결과로 고정한다. 저장 문서의 다른 필드는 화이트리스트 선택에서 제외한다. 필요한 값 누락·비정상 자료형을 0으로 채우지 않는다.

feature_spec에는 버전·열 이름/순서/자료형·추출 원천·전처리 정의를 담는다. 학습·추론은 이 스펙을 공유한다. 호출자가 전달한 완성된 피처 표의 누락·추가·순서 불일치는 오류로 처리하며, 어댑터는 처음부터 스펙 순서로 표를 만든다.

### 라벨과 분할

사용자 결정에 따라 같은 카드의 각 등록 포지션에 동일 X를 연결하는 단일 클래스 학습 행을 만든다. 모델은 이 경우에도 다중 라벨 전용 모델이 아니라, 기존 방식의 다중 클래스 확률 모델이다. 학습한 클래스 순서와 position code 매핑을 매니페스트에 기록한다. 원시 카드 표와 펼친 학습 행의 개수를 혼동하지 않는다.

분할은 전처리 fit 이전에 수행하고, 같은 spid의 펼친 행이 train/test에 동시에 들어가지 않게 한다. Stage 2-B에서는 spid 그룹과 person_id 그룹을 각각 평가하는 기존 설계 제안을 별도로 다룬다. 분할 비율·시드·평가 기준은 이번 설계에서 새 사용자 결정으로 확정하지 않는다. 기존 2024 설정은 재현 비교 대상이며 새 기본 평가의 정답으로 취급하지 않는다.

학습한 클래스만 출력 계약의 확률 공간으로 삼고 순서를 보존한다. 현재 자료에서는 15종이지만 모든 버전에 15종을 하드코딩하지 않는다. 학습되지 않은 슬롯을 조용히 변환하거나 확률 0으로 추가해 지원한다고 보고하지 않는다. Stage 3의 배치 확장은 D5와 별도 계약이다.

### 공통 변환·추론

숫자 변환·스케일러·체형 인코더를 하나의 버전된 변환 묶음으로 저장한다. 학습 분할에서만 fit하고 검증·추론에서는 transform만 사용한다. 새 입력의 미학습 체형은 자동 학습·범주 확장 대신 오류로 보고하는 안이다. 구체 인코더 구현은 기존 재현 결과와 함께 검토한다.

추론은 누락된 카드·충돌 버전·잘못된 피처를 명시적 오류로 보고한다. 모델이나 변환기가 없거나 버전·파일 해시가 맞지 않으면 실패하며 요청 처리 중 학습하지 않는다. 현재 레거시 Classifier.call의 자동 학습을 새 경로에서 사용하지 않는다.

전체 확률 응답은 model_version, position class 순서, spid별 클래스 확률을 포함한다. 클래스 열은 인코더의 역변환과 대응해야 하며 NaN·무한대·음수·1 초과·행 수/열 수 불일치를 거부한다. 합이 1인지 수치 오차 허용 범위에서 검사한다. 기존 0.1 임계값 목록은 이 확률에서 파생하는 호환 함수로 분리한다. 임계값을 성능 점수나 D5 허용 규칙으로 확정하지 않는다.

### 재현 매니페스트

매니페스트에는 계약 버전, feature_spec, 클래스 목록/순서, 입력 배치와 관측/데이터 해시, 기준 강화, 라벨 정책, 분할 그룹·시드·행 수, 변환기·모델 설정, 런타임·라이브러리 버전, 파일별 SHA-256을 포함한다. 학습에 쓴 데이터의 추천 신선도 미확정도 표시한다.

해시는 UTF-8·정렬 키·고정 JSON 직렬화로 계산하며 model_version 자체는 해시 입력에서 제외해 순환 참조를 피한다. 모델/변환 파일의 해시는 먼저 계산해 매니페스트에 담는다. 변경된 피처·클래스 순서·파일·배치는 다른 model_version이 된다.

모델·변환기·전체 학습 매니페스트는 D2에 따라 Git 제외 로컬 artifacts/models에 보관한다. 이번 설계는 파일을 생성하거나 기존 pickle을 불러오지 않는다.

## 구현 후 필요한 검증

- 가상 카드·수치만 사용한 화이트리스트/열 순서/자료형·누락·중복·충돌 검사.
- 별도 식별자와 등록 포지션이 X로 들어가지 않는지 확인.
- 선택한 라벨 정책의 행 수·라벨 대응·그룹 보존, train/test 그룹 겹침 검사.
- 학습 변환기의 고정 입력 결과가 저장·로드 후 추론에서도 일치하고, test 자료가 fit에 영향을 주지 않는지 확인.
- 새 확률 계약의 클래스 매핑·합·유한성·오류, 모델 부재 시 자동 학습이 없는지 검사.
- 매니페스트 결정성, 파일 변조·클래스/피처/라이브러리 불일치 거부 검사.

이 테스트 목록을 실제로 통과했다고 보고하지 않는다. 이 문서는 설계 산출물이며 2-A 재학습·2-B 평가·2-C API·2-D 재현 스크립트는 후속 범위다.

## 이번 설계 작업의 검증과 완료 범위

문서 경로·상대 링크, 기존 코드의 실제 동작, 34개 능력치 이름/순서와 6개 부가 피처의 합계 40개, 사용자 답변과 설계도 §5·§11·개발 지침의 일치를 확인했다. 문서만 변경하여 로컬 기능 테스트는 재실행하지 않았다. 기존 코드의 pytest 268개·Ruff·MongoDB 합성 통합 검증은 PR #16에서 통과했으며 이번 PR의 최신 원격 CI는 별도로 확인한다.

세 정책의 설계 결정은 완료했다. 어댑터·공통 변환·출력 계약·매니페스트의 코드와 계약 테스트는 미구현이므로 **Stage 2-0 전체는 미완료**다. Stage 1-D·1-F도 미완료로 유지한다. 다음 구현 작업에서 이번에 확정한 세 정책을 다시 질문하지 않는다.
