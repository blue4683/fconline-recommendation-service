# Stage 3-A 포지션별 OVR 성능 점수 계약 설계

2026-10-19 사용자 결정으로 1-D·1-F 미완료를 유지하고 **성능 점수 계약 설계만** 먼저 정리한다. 설계 선행 당시 scorer/solver 코드·새 수집·실데이터 적재·학습은 제외했다. 이후 사용자가 성능 점수 계약 코드와 합성 단위 테스트를 별도로 승인했으며 실제 코드는 후속 기능 PR에서 구현한다. DB/외부 요청·실데이터 점수 실행·학습·배치 허용·solver·API 연결은 계속 제외한다. 현재 D1 실데이터 경로는 유지하며 설계 예시는 가상 값만 사용한다.

## 확정한 사용자 결정

- D7 근거는 **선택한 강화의 포지션별 OVR**이다. 등록 포지션 분류 확률·가격·급여·능력치 가중합으로 성능 점수를 대체하지 않는다.
- 운영 정규화는 **performance = OVR / 2**, 기준 상한은 200이다. 200은 공식 게임 상한이 아니라 이번에 선택한 프로젝트 기준이다. 원시 OVR도 함께 보존하고, 범위 밖 수치를 100으로 자르지 않는다.
- 아래 좌우 슬롯 대응은 **OVR 조회 키에만** 적용한다. 좌우 등록/배치 허용, 모델 확률 확장, 포지션 적합성을 승인한 것은 아니다.
- OVR 누락·범위 오류이면 **해당 카드·슬롯만 제외**하고 사유를 보고한다. 다른 조합은 계속 평가하고 다른 강화·등록 OVR·능력치·모델 확률로 보충하지 않는다.

| 요청 슬롯 | 사용할 OVR 키 |
|---|---|
| RCB, LCB | CB |
| RDM, LDM | CDM |
| RCM, LCM | CM |
| RAM, LAM | CAM |
| RS, LS | ST |
| 나머지 지원 슬롯 | 같은 코드 |

대응식은 `ovr_key = aliases.get(slot, slot)`이다. 예를 들어 RCB의 점수를 조회하면 CB 값을 사용한다. 대응 대상 키가 없을 때 다른 키를 자동 탐색하거나 RF/LF를 RW/LW로 확장하지 않는다. 이 정책을 바꾸려면 점수 규칙 버전도 바뀌어야 한다.

## 현재 코드·저장 자료에서 확인한 사실

이번에는 기존 가공 파일을 읽어 구조와 집계만 확인했고 외부 요청은 하지 않았다. `stage-1-d-enrichment-20261019`에는 기본 5강 카드 259개·강화 관측 1,813개(5~11 각 259개)가 있다. 모든 OVR 맵에는 **공통 포지션 16종**이 있고 기본 관측 범위는 24~132, 강화 전체는 24~147이다. 이 표본의 범위가 게임 전체 범위를 뜻하지 않는다. 원본의 unknown·시각·기한을 변경하지 않았다.

OVR 키는 CAM·CB·CDM·CF·CM·GK·LB·LM·LW·LWB·RB·RM·RW·RWB·ST·SW다. 반면 `FRS/schema/scope.py`의 MVP 슬롯에는 RCB·LCB·RDM·LDM·RCM·LCM·RAM·LAM·RS·LS가 있다. 따라서 점수의 좌우 키 대응과 배치 허용 규칙을 분리해야 한다. 등록 포지션 RF에 해당 OVR 키가 없는 관측도 1개 있다. 이 하나를 다른 포지션으로 자동 보정하지 않는다.

`ability_parser.reinforcement_delta`의 stats_delta는 차이값이지만 **ReinforceStats.position_ovr는 해당 강화의 절대 OVR**이다. 기본값에 강화 OVR을 다시 더하면 잘못된 점수가 된다. 기존 1-E는 정확 등록 포지션 검색이며, 이 설계의 OVR 대응을 검색 조건이나 모델 클래스 확장에 자동 적용하지 않는다.

## 후속 코드의 입력·출력 설계안

입력은 명시한 스냅샷의 카드 관측, 필요한 강화 관측, 목표 강화, 목표 슬롯, 기준 시각 t0다. 기존 Candidate의 관측을 재사용할 수 있지만 슬롯별 후보 조회와 스냅샷 고정은 3-0·D5와 별도로 연결해야 한다. scorer 안에서는 DB·네트워크·학습·최신 선택을 하지 않는다.

1. 요청 슬롯·강화·기준 시각과 관측의 spid/버전/기준 강화를 확인한다. 현재 지원 강화는 5~11이다. 기본 관측과 강화 관측의 연결이 다르면 점수를 만들지 않는다.
2. 목표 강화가 PlayerCard.base_reinforce_level과 같으면 **PlayerCard.position_ovr**를 사용한다. 높으면 해당 강화의 **ReinforceStats.position_ovr**를 사용한다. 기본 관측 버전/강화 연결을 확인하고, 다른 강화의 값이나 stats_delta로 OVR을 추정하지 않는다.
3. 기존 신선도 계약에 따라 사용하는 관측이 t0에서 유효해야 한다. unknown/만료 자료의 오프라인 학습 허용을 현재 추천 점수 허용으로 확대하지 않는다.
4. 확정한 슬롯 대응으로 키를 정하고 정수 OVR을 확인한다. 유효 범위는 1~200이며 누락·유효 범위 밖은 카드·슬롯 제외다. 구조/자료형이 깨진 문서는 데이터 경계의 공통 검증으로도 거부한다.
5. 점수는 OVR/2로 계산한다. 반올림·클리핑·후보 집합 기준 재조정은 하지 않는다. 같은 OVR은 후보 수와 관계없이 같은 점수다. 화면 표시 반올림이 필요하더라도 원래 점수는 보존한다.

성공 결과에는 spid·목표 강화·요청 슬롯·실제 OVR 키·원시 OVR·performance·점수 규칙 버전과 사용 관측의 batch_id/version/observed_at/valid_until을 담는 안이다. 제외 결과에는 카드·강화·슬롯과 기계적으로 구분할 사유를 담는다. 실패를 0점 성공이나 후보 전체 누락으로 숨기지 않는다.

후속 코드의 사유 이름 예시는 missing_ovr, ovr_out_of_range, missing_reinforcement, baseline_mismatch, unusable_observation이다. 구조가 잘못된 요청과 유효한 요청 안에서 특정 카드·슬롯이 제외되는 경우를 구분한다. 정확한 Python/HTTP 스키마는 코드 구현 범위에서 고정한다.

점수 규칙 버전에는 OVR 근거·상한 200·계산식·별칭 표·누락 제외·강화 선택 규칙이 연결되어야 한다. 구체적인 버전 식별 방식은 구현안에서 정하되 서로 다른 점수 규칙을 같은 버전으로 보고하지 않는다. 관측 버전과 점수 규칙 버전은 별개다.

## 가상 예시와 필요한 검증

| 가상 입력 | 기대 결과 |
|---|---|
| 5강 CB OVR 120, 요청 슬롯 RCB | OVR 키 CB·점수 60. 배치 허용 여부는 별도 |
| 7강 CB 절대 OVR 128, 기본 5강 OVR 120 | 점수 64. 120+128로 계산하지 않음 |
| OVR 200 | 점수 100 |
| OVR 201 | 해당 카드·슬롯 범위 오류 제외. 100점으로 클리핑하지 않음 |
| 대응 키의 OVR 누락 | 해당 카드·슬롯 누락 제외. 다른 포지션/강화로 대체하지 않음 |
| 같은 값의 후보를 추가/제거 | 기존 카드의 점수 불변 |
| unknown 또는 만료 능력치 | 원본 상태를 바꾸지 않고 사용 불가로 보고 |

후속 합성 테스트에는 양 끝 범위·자료형·공통/좌우 슬롯·강화 절대값·다른 카드/기준 버전·미상/만료 경계·누락 및 부분 제외·입력 불변·외부 I/O 부재를 포함해야 한다. 아직 scorer 코드를 작성하거나 이 테스트를 실행하지 않았으므로 구현/검증 완료로 기록하지 않는다.

## 남은 결정과 한계

이번 문서는 **3-A 성능 부분의 계약 설계**다. 3-A 전체나 Stage 3을 완료한 것이 아니다. D5의 배치 허용·동일 인물 판정·팀컬러 발동, 모델 확장 임계값/감점, D4 솔버 방식, D6 성능/E2E 성공 기준은 미확정이다. 3-0 스냅샷과 응답 시 만료 처리도 아직 연결하지 않았다.

특히 공통 CB 점수를 RCB에 조회할 수 있다는 사실은 CB 등록 선수를 RCB에 배치할 수 있다는 판정이 아니다. 현재 정확 등록 검색·15개 분류 클래스·미학습 좌우 확장 금지는 유지한다. 부족한 후보를 배치 확장이나 추정 OVR로 채우지 않는다. Stage 1-D·1-F와 제공자 허용의 미완료 상태도 유지한다.
