# Stage 4-A 조건 정규화 계약 설계

2026-10-20 사용자 결정. 1-D·1-F 미완료를 유지하고 Stage 4-A 계약 설계를 먼저 진행한다. 이번 범위는 문서이며 코드 구현·LLM 공급자/모델 선택·유료 호출·새 수집·실데이터/DB·API 연결을 포함하지 않는다. 앞선 단계 선행 조건보다 이번 설계 전용 결정을 우선한다.

## 확정한 제품 계약

| 항목 | 사용자 결정 |
|---|---|
| 필수 조건 | 예산·급여 상한·클럽·포메이션·허용 강화 집합 5개 모두 원문에 명시 |
| 누락 | 되묻기. 기본값·다른 조건·과거 요청으로 보충하지 않음 |
| 자료 선택 | 자료별 배치 ID는 자연어에서 추출하지 않고 내부의 명시 선택과 분리 |
| 금액 문법 | 아라비아 숫자와 십/백/천·만/억/조/경, 올바른 쉼표/공백·소수 표기 |
| 금액 정확도 | 정수 BP로 정확히 표현되는 경우만 허용. float 반올림/단위 절삭 없음 |
| 금액 모호성 | 약/내외·금액 범위·복수 충돌은 되묻기 |
| 미지원 조건 | 선수 제외·국적·빠른 선수 등 현재 엔진에 없는 조건을 무시하지 않고 항목/지원 목록 반환 |

현재 지원 값은 클럽3종(리버풀·첼시·바이에른 뮌헨), 포메이션3종(4-2-3-1·4-1-2-3·4-2-2-2), 강화5~11이다. 같은 person_id 최대1명·전원 선택 클럽 자격·기본 배치·상한 합계 등 엔진 계약은 유지한다. 자연어에서 별칭·다른 범위·기본값을 임의로 추가하지 않는다. 공식 발동 단계/능력치 보너스는 아직 지원하지 않는다.

## 설계안: 추출과 정규화 경계

아래 입출력 구조는 구현 전 계약 초안이다. LLM 사용/스키마 코드 구현 완료로 보고하지 않는다.

1. 추출 입력은 원문 하나다. 추출기는 조건 종류와 원문 구간을 제시하고 금액 숫자를 직접 산출하지 않는다. 불명확/미지원 단서도 원문 근거와 함께 남긴다.
2. 코드가 원문 구간과 금액/값을 검증·정규화한다. 원문에 없는 내용이나 잘못된 구간은 오류로 다루며 다른 문자열을 찾아 자동 복구하지 않는다.
3. 누락·모호성·미지원·구간/문법 오류를 issues로 모은다. issues가 남아 있으면 완성 요청이나 스쿼드를 만들지 않는다. 여러 종류가 동시에 있으면 각 사유를 보존하며 최종 API의 단일 상태 우선순위는 후속 계약이다.
4. 완성된 조건과 내부 BatchSelection·기준 시각을 결합해 SnapshotQuery를 만든다. 배치 선택·최신 관측 선택을 LLM에게 맡기지 않는다.

구간 구조는 field, start, end, text를 제안한다. 인덱스는 Python str의 유니코드 코드포인트 기준, 0부터 시작하며 end 미포함이다. `original[start:end] == text`를 원문 수정 전에 확인한다. UTF-8 바이트/브라우저 UTF-16 인덱스와 혼용하지 않는다. 같은 값이 반복돼도 다른 출현 위치로 바꿔 근거를 대체하지 않는다.

금액 원문과 정규화 결과는 함께 보관한다. 쉼표/공백 제거·단위 해석은 구간 검증 뒤 별도 파서에서만 수행한다. 소수는 Decimal 또는 유리수 방식으로 계산하고 최종 정수 여부·범위를 확인한다. 파서는 조각 일부만 읽고 남은 단어를 버리지 않아야 한다. 예산 범위는 기존 0~10^34-1 BP, 급여 상한은 기존 비음수 정수 계약이며 이는 공식 게임 상한이라는 뜻이 아니다.

## 필드별 정규화 초안

| 원문 조건 | 정규화 결과 | 남은 확인/제한 |
|---|---|---|
| 예산 | price_cap 정수 BP와 원문 근거 | 명확한 상한만 사용. 범위/약/충돌은 되묻기 |
| 급여 상한 | salary_cap 비음수 정수와 근거 | 임의의 게임 급여 기본값/상한을 넣지 않음 |
| 클럽 | team_color 정식 지원명과 근거 | 별칭 표는 미확정. 경력/국적을 자격으로 대체하지 않음 |
| 포메이션 | 지원 formation과 근거 | 4231 등 축약/별칭 문법은 미확정 |
| 강화 집합 | allowed_reinforcements의 명시 정수 집합 | 5~11 범위만 지원, 범위/목록/중복의 자세한 문법은 구현 전 확인 |

예산 `1조 5천억`과 `1.5조`는 각각1,500,000,000,000 BP, `150,000BP`는150,000 BP다. `0.0000000000001조`는0.1 BP이므로 정수로 표현되지 않아 반올림하지 않고 수정을 요청한다. `약1조`, `1조~2조`, 서로 충돌하는 복수 예산은 한 숫자로 임의 확정하지 않는다. 소수 자릿수·쉼표 오류·단위 중복/역순·공백 유형 등 완전한 문법과 입력 길이 제한은 구현 전 별도로 확인해야 한다.

예를 들어 `리버풀 예산 1.5조`에는 급여·포메이션·강화가 없어 되묻는다. 필요한 나머지 조건이 모두 있어도 `선수A 제외`나 `국적 조건`이 추가되면 지원하지 않는 조건을 반환하고 제외 요구를 지운 스쿼드를 생성하지 않는다. 예시의 선수A는 가상 표시이며 실존 선수명이 아니다.

## 보장 범위와 후속 확인

원문 구간이 실제로 존재해도 추출기가 예산과 급여를 바꿔 읽거나 부정을 잘못 해석할 수 있다. 스키마/부분 문자열 검증 통과를 의도 정확성으로 간주하지 않는다. Stage 4-D에서는 원문과 정답 구조화 조건의 필드 일치를 따로 평가해야 한다. LLM이 미지원 조건을 아예 추출하지 않는 경우까지 현재 설계만으로 검출한다고 주장하지 않는다.

이번 설계에서는 공급자/모델·계정/비용·SDK·유료 검증을 정하지 않는다. 금액/강화의 완전 문법·별칭·구간 오류 처리/재추출 횟수·issues의 최종 응답 우선순위·길이 제한·4-D 의미/E2E 수치 기준은 미확정이다. 코드 구현은 별도 사용자 범위 확인 후 진행하고 이 문서의 제안을 확정 결정으로 자동 편입하지 않는다.

수집/실데이터/DB/API·학습·모델 확장·공식 팀컬러 발동/보너스와 1-D·1-F 미완료는 유지한다.

후속 승인으로 [원문 구간·금액 계약](stage-4-a-amount-contract.md)의 순수 코드 범위만 확대했다. 기존 설계 전용/세부 미정 중 해당 항목은 후속 사용자 결정을 우선한다.
