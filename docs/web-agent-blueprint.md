# 웹 담당 에이전트 설계도

작성일: 2026-10-20. 대상은 합성 가상 리그의 Agent MVP이며 로드맵 W2/W4의 웹 부분이다. 이 문서는 작업 인계용 설계다. 현재 저장소에는 프론트엔드 앱·Agent 채팅 API·SSE 계약 구현이 없다.

## 1. 확정 사항과 착수 순서

사용자 확정:

- Vue 3 + Vite + TypeScript 독립 프론트엔드를 사용한다.
- 웹 담당은 화면·통신 클라이언트만 구현한다. 모의 응답으로 먼저 개발하며 엔진·Agent·API 수정과 실제 연결은 통합 담당이 전담한다.
- 설계와 다른 점·공유할 정보는 [공용 기록](agent-collaboration.md)에 남긴다. 기존 엔진/Agent를 웹 요구에 맞춰 직접 수정하지 않는다.

읽는 순서는 루트 [AGENTS.md](../AGENTS.md) → [과제 로드맵](ai-mini-project-roadmap.md) → 이 문서 → [프론트엔드 지침](../frontend/AGENTS.md) → 공용 기록이다. 상위 지침과 충돌하면 상위 지침을 따르고 충돌을 기록한다. 사용자 초안 ai-mini-project-plan.md는 수정/커밋하지 않는다.

1. 최신 develop과 공용 기록에서 배정 범위·계약 버전·차단 항목을 확인한다.
2. 별도 작업 디렉터리와 `feat/squad-web-ui` 같은 작업 브랜치를 사용한다. 다른 에이전트가 사용하는 디렉터리에서 브랜치를 전환하거나 파일을 수정하지 않는다.
3. 웹 전용 런타임·의존성 버전은 호환성을 확인해 고정하고 공용 기록에 제안한다. 아직 Node/npm/Vue/Vite/TypeScript/테스트 도구의 정확한 버전은 미정이다. 설치/실행 지침을 임의로 완료 상태로 쓰지 않는다.
4. 아래 v0를 **모의 응답용 제안**으로 사용한다. 실제 네트워크 연결은 통합 담당이 확정 계약·백엔드 PR·접속 정보를 기록한 뒤 진행한다. 계약 확정 전에는 API가 존재한다고 가정하지 않는다.

## 2. 수정 범위와 소유권

| 구분 | 웹 담당 권한 |
|---|---|
| frontend/의 앱·스타일·컴포넌트·클라이언트·모의 자료·테스트·README·전용 package/lock 파일 | 웹 범위로 수정 가능 |
| frontend/AGENTS.md | 읽기 전용. 작업 범위를 스스로 넓히는 수정 금지 |
| docs/agent-collaboration.md | 자기 WEB-* 기록을 추가/갱신. 타 담당의 기록·확정 계약 표를 임의 수정하지 않음 |
| FRS/core/·FRS/schema/·FRS/agent/·FRS/api/·FRS/utils/·FRS/diagnostics/ | 읽기 전용. 아직 없는 FRS/agent/에도 새 파일을 만들지 않음 |
| 기존 tests/·scripts/·requirements*·pyproject.toml·Docker/Compose·.github/·루트 설정 | 읽기 전용. 웹 테스트는 frontend/ 안에 둠 |
| 루트 AGENTS.md·README·기준 설계도·이 설계도·로드맵·인수인계 | 통합 담당 소유. 변경 요청은 공용 기록으로 전달 |
| 수집 원본·가공 데이터·모델·비밀값 | 읽기/복사/수정/커밋 대상 아님. 웹용 자료는 가상 fixture만 사용 |

파일 이동·삭제·이름 변경·심볼릭 링크·설치 후 스크립트로 보호 경로를 간접 수정하는 것도 금지한다. Python 엔진을 JS로 복제하거나 테스트를 약화해 화면에 맞추지 않는다. PR 경계 확인은 생성/수정뿐 아니라 삭제/이동의 이전 경로도 포함한다.

권장 폴더 구조는 frontend/src/{components,views,services,contracts,mocks}와 frontend/tests/다. node_modules·dist·캐시·실제 .env는 frontend/.gitignore로 제외하고 버전 고정용 lock 파일은 커밋한다. transport 인터페이스의 mock/live 구현을 분리한다. live 구현도 HTTP 클라이언트이며 Python·DB·Ollama를 직접 호출하지 않는다. 기존 FastAPI를 대신하는 웹용 Python 서버나 BFF를 만들지 않는다.

## 3. 화면 범위

한 화면에서 다음을 제공한다. 디자인·컴포넌트 내부 구조는 웹 담당이 정할 수 있지만 기능/데이터 정책은 확대하지 않는다.

| 영역 | 표시/동작 |
|---|---|
| 안내 | 항상 합성 가상 데이터임을 표시. mock 모드와 실제 Agent 연결 모드를 구분 |
| 요청 입력 | 한국어 원문 한 개와 필수 5조건 안내. 요청 예시를 선택해도 사용자가 확인/전송하며 숨은 기본값을 넣지 않음 |
| 진행 상태 | extract/normalize/build/render/narrate/check 등 서버가 보낸 단계만 표시. 가짜 진행률·검증 전 답변 표시 금지 |
| 결과 | 코드가 확정한 11명 표·예산/급여 상한·합계·상태·스냅샷 시각·기한·검사된 설명 |
| 안내/실패 | 누락/미지원/모호성·해 없음·미확정·만료·내부 오류·통신 오류를 구분 |

정식 지원값은 리버풀·첼시·바이에른 뮌헨, 4-2-3-1·4-1-2-3·4-2-2-2, 추천 5~11강이다. 능력치 계산 가능 범위 1~13강을 추천 지원으로 표시하지 않는다. 선수명·능력치·가격 fixture는 가상이다. 클럽 레이블은 기존 지원 조건을 사용하되 실제 팀컬러 보너스가 적용된다고 표시하지 않는다.

기본 흐름은 독립된 단일 요청이다. 누락 안내를 받으면 완전한 요청을 다시 입력한다. 이전 대화와 새 예산을 합치거나 별칭·선수 제외·세션 저장·자동 재추천을 구현하지 않는다. 전송 시 원문을 치환/요약/정규화하지 않는다. 공백뿐인 입력은 전송하지 않고 입력 길이를 자르지 않는다. 서버의 Python 코드포인트 기준 4,000자를 유지하며 JS의 UTF-16 길이와 혼동하지 않는다.

BP·가격·급여·합계는 서버가 준 정확한 값을 표시한다. 클라이언트가 후보를 고르거나 가격을 보정하거나 예산을 나누어 보내지 않는다. 이름/설명/오류는 텍스트로 렌더링하고 v-html 등으로 HTML을 실행하지 않는다. 전체 프롬프트·추론 과정·비밀값은 표시/저장하지 않는다.

## 4. 웹 경계 v0 — 모의 구현 제안

식별자: `web-agent.v0`. 아래는 현재 구현된 API나 확정 서비스 계약이 아니다. 웹 모의 개발과 통합 담당 검토를 위한 구체안이다. 제품 범위/비용/새 정책 결정은 사용자 확인이 필요하며, 단순 DTO/전송 조정은 공용 기록에서 양쪽 영향과 적용 버전을 확인한 뒤 통합 담당이 기준을 갱신한다.

### 요청과 전송

- 제안 경로: `POST /recommend/squad/stream`, JSON body `{contract_version, request_id, message}`. 원문은 query string에 넣지 않는다.
- request_id는 클라이언트가 요청마다 부여하는 불투명 문자열이며 서버가 검증/반환한다. 중복 실행 방지나 취소를 보장하는 키로 해석하지 않는다.
- 명시 배치·모델·시계·합성 자료 선택은 서버 소유다. 브라우저가 배치·solver 설정·스냅샷 내용·검증 통과 플래그를 요청으로 보내지 않는다.
- 응답은 UTF-8 text/event-stream을 읽는 POST 스트림 클라이언트 안이다. 자동 재연결/자동 재전송은 꺼둔다. HTTP 비정상 응답과 스트림 시작 뒤 오류를 구분한다.
- base URL·허용 origin·포트·CORS·proxy·서버 실행 명령은 아직 미정이며 통합 담당이 기록한다. 기존 /health를 Agent 준비 상태로 추측하지 않는다. 기존 세 API와 충돌하는 서버/경로를 만들지 않는다.

### 이벤트와 종료

공통 envelope는 `{contract_version, request_id, seq, type, payload}`다. SSE event 이름과 type은 같고 seq는 요청 안에서 0부터 연속 증가한다.

| type | payload의 의미 | 웹 표시 |
|---|---|---|
| started | 요청 수락, data_mode=synthetic | 실행 시작. 추천 성공을 뜻하지 않음 |
| progress | stage와 사용자용 message | 진행 단계 텍스트만 |
| final | 아래 최종 결과 DTO | 검사/최종 기한 확인을 마친 결과를 한 번에 표시 |
| error | code와 안전한 message | 기술 오류. 성공 표 없음 |

final 또는 error가 종료 이벤트다. 서버는 정확히 하나만 보내고 종료한다. final에는 표와 설명을 함께 넣으며 별도 토큰 스트림·부분 스쿼드를 먼저 공개하지 않는다. 서버는 서술 검사 뒤 최종 만료 확인까지 마쳐야 final을 보낸다.

청크는 이벤트 경계나 한글 문자 경계와 일치한다고 가정하지 않는다. UTF-8 분할·여러 이벤트·여러 data 행·빈 줄 종료·CRLF·주석 heartbeat를 파서에서 처리한다. 모르는 버전/필수 이벤트·잘못된 JSON/필드·번호 누락/역전은 프로토콜 오류로 처리한다. 이전 요청 ID의 늦은 이벤트는 현재 화면을 갱신하지 못한다. 종료 전 EOF는 통신 오류이며 해 없음으로 바꾸지 않는다.

화면 한 개에서는 진행 중 중복 전송을 막는다. 연결 종료가 서버 계산 취소를 뜻한다고 표시하지 않는다. 서버의 동시 실행/중복/취소 정책은 별도 확정 사항이며 자동 재시도 버튼이나 재연결로 우회하지 않는다. 재시도는 자동 실행하지 않고 새 요청으로 사용자가 명시적으로 전송하는 방식이다.

### 최종 결과 DTO 제안

| 필드 | 타입/규칙 |
|---|---|
| status | needs_clarification / optimal / feasible / infeasible / unknown / data_expired / internal_error / llm_unavailable 제안 |
| conditions | 정규화 성공 시 5조건. price_cap·salary_cap은 정확한 10진 정수 문자열, 강화는 작은 정수 배열 |
| issues | 기존 ConditionIssue의 field/kind/code/message/occurrence. 미지원도 needs_clarification의 issues로 구분 |
| supported | 정식 클럽/포메이션/강화/필수 필드 목록. 서버 제공값을 표시 |
| squad | optimal/feasible에서만 존재. 검증된 rows 11개·total_price·total_salary·total_ovr·performance |
| rows의 각 행 | slot, spid, person_id, name, reinforce_level, price, salary, raw_ovr, performance, placement_type |
| snapshot | 엔진 실행 시 id·t0·valid_until. 성공에서는 기한이 있는 스냅샷을 명시 |
| versions | 웹 계약·정규화·엔진·모델 등 적용한 버전. 모델을 쓰지 않았으면 미사용을 명시 |
| answer | 검사된 설명 또는 코드 안내 텍스트. 원본 LLM 초안 없음 |
| narration_source | llm_checked / template / none 제안. 실제 사용한 경로만 표시 |
| data_mode | synthetic. mock/live 연결 모드는 클라이언트에서도 별도로 표시 |

모든 금액과 급여·상한·합계, spid/person_id/snapshot_id는 DTO에서 문자열로 운반하는 안이다. BP는 최대 34자리, 급여는 2^63-1까지의 기존 범위를 보존한다. JSON number로 받은 후 문자열로 바꾸면 이미 정밀도를 잃었을 수 있으므로 Number/parseFloat 변환을 하지 않는다. 표시용 쉼표는 문자열로 처리하며, 계산이 꼭 필요해도 서버 검증을 대신하지 않는다. 강화·OVR·행 개수 같은 작은 정수와 기존 0.5 단위 점수만 number를 사용할 수 있다.

시각은 시간대가 있는 ISO 8601 문자열이다. SourceSpan이 제공되면 start/end는 Python 코드포인트·끝 제외이며, 브라우저가 근거를 재검색하거나 UTF-16 인덱스로 원문을 잘라 대체하지 않는다. 웹 전용 직렬화는 통합 담당의 어댑터가 수행한다. 이 형식을 맞추기 위해 기존 Python 도메인 모델의 정수나 검증기를 변경하지 않는다.

기존 cp_sat 결과에는 optimal/feasible/infeasible/unknown/internal_error/data_expired가 있다. 비교 탐욕의 greedy_failed는 이 경로의 성공 상태가 아니다. DTO의 llm_unavailable 등은 새로운 웹 경계 제안이며 현재 엔진에 이미 있다고 기록하지 않는다.

## 5. 표시 불변 조건

| 결과 | 허용되는 화면 |
|---|---|
| needs_clarification | 누락·미지원·모호/오류 사유와 지원 목록. 스쿼드 표 없음 |
| optimal | 검증된 11명 표와 최적 확인. 실제 경기 성능 보장으로 표현하지 않음 |
| feasible | 검증된 11명 표와 최적성 미확인. 임의로 optimal로 바꾸지 않음 |
| infeasible | 보유 자료 기준 해 없음·가능하면 커버리지. 조건 자체가 영원히 불가능하다고 표시하지 않음 |
| unknown | 시간 내 결론 미확정. 해 없음으로 표시하지 않음 |
| data_expired | 만료 안내. 성공 표/설명을 내보내지 않음 |
| internal_error / llm_unavailable / 통신·프로토콜 오류 | 오류 안내. 이전 성공 결과가 이번 요청의 결과로 남지 않음 |

서버 final의 status·squad 유무·행 개수·필수 기한 등의 경계가 맞지 않으면 성공 표시를 거부하고 프로토콜 오류로 처리한다. 클라이언트의 구조 검사는 서버 독립 검증기의 대체가 아니다. 이미 표시한 결과도 기한 경과를 감지하면 만료로 표시하고 현재 추천으로 재사용하지 않는다. 브라우저 시계로 유효성을 확정하거나 자동 갱신하지 않으며 화면 복귀 시에도 만료를 확인한다.

## 6. 모의 자료와 검증

mock 모드는 명시적으로 선택하며 live 실패 시 몰래 mock 성공으로 바꾸지 않는다. 정상 fixture는 서로 다른 가상 인물 11명·정식 포메이션 슬롯·5~11강·정확한 합계를 사용한다. 실제 선수명/수치·원본 HTML/JSON·모델을 복사하지 않는다. 고정 테스트 시계와 서비스 실행 시각을 분리하고 시한을 임의로 연장하지 않는다.

필수 검증 사례:

- 정상 optimal/feasible, 누락·미지원·모호성, 해 없음·미확정·만료·모델/통신 오류를 각각 표시.
- 34자리 BP와 2^53 초과 급여를 손실 없이 표시. 예산/급여 값을 브라우저에서 고치지 않음.
- 이모지 포함 원문·4,000 코드포인트 경계·원문 공백 보존·근거 인덱스 처리.
- 여러 SSE 청크/이벤트·한글 분할·CRLF·heartbeat·잘못된 JSON/버전·중복/역전·종료 전 끊김·이전 요청의 늦은 이벤트.
- final 전 표/서술 미노출, 실패/기한 경과 시 이전 표가 현재 성공처럼 보이지 않음, 자동 재전송 없음.
- HTML처럼 생긴 이름/답변을 텍스트로 표시. 키보드 입력/전송·레이블·좁은 화면의 표 스크롤 확인.

선정한 프론트엔드 도구로 타입 검사·동작 테스트·빌드를 실행하고 버전/명령/결과를 frontend/README와 공용 기록에 적는다. 아직 package/lock/스크립트가 없으므로 npm ci·typecheck·test·build를 실행했다고 보고하지 않는다. 향후 npm script 이름과 CI 추가는 통합 담당과 확정한다. 웹 PR도 루트 AGENTS.md의 Python 전체 pytest·Ruff 검증을 유지한다.

## 7. 백엔드 변경 요청과 병합 게이트

1. API 부재·DTO 불일치·CORS·타임아웃·도메인 오류를 발견하면 WEB-* 기록에 재현 조건, 기대/실제 결과, 영향 파일/계약, 필요한 변경과 임시 mock 상태를 적는다.
2. 웹은 보호 파일을 직접 수정하지 않는다. 의존하지 않는 UI/모의 테스트를 계속하고 해당 연결만 대기한다.
3. 통합 담당은 요청을 확인하고 필요한 백엔드 변경을 별도 PR로 구현/검증한다. 제품/지원 범위·데이터 정책을 바꿔야 하면 사용자에게 질문한다.
4. 백엔드 PR이 develop에 병합되고 공용 기록에 적용 버전·SHA·검증이 남으면 웹 담당이 새 develop을 반영해 클라이언트를 조정한다. 상대 작업 브랜치를 몰래 가져와 계약이 배포된 것으로 간주하지 않는다.
5. 통합 담당이 웹 PR의 실제 전체 변경 경로/공용 기록 수정 범위·최신 head CI·mock/live 표시·원문/수치/검증/만료 경계를 확인한 뒤 develop에 Squash 병합한다. 다른 에이전트는 병합을 동시에 진행하지 않는다.

`git diff --name-status origin/develop...HEAD`로 로컬 범위를 확인하고 원격 PR 파일 목록도 대조한다. 보호 파일 변경이 섞였으면 검토에서 제외해 숨기지 말고 사유를 기록하고 작업자와 해결한다. 다른 사용자의 변경을 임의로 되돌리거나 이력을 재작성하지 않는다.

폴더 소유권·AGENTS.md는 협업 규칙이며 OS 파일 권한 격리나 CI 강제 차단이 아니다. 현재 CI는 Python 검증만 수행한다. 변경 경로 자동 차단·웹 CI는 통합 담당의 후속 구현 항목이며, 이를 도입하기 전까지 PR diff 확인을 생략하지 않는다.
